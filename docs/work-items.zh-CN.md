# 工作项与阶段验收

新会话中的执行计划按独立工作项运行，不再把所有成员依次发言等同于任务执行完成。成果与过程面板可以查看负责人、复核人、前置依赖和逐条验收记录。

- 只有前置工作通过阶段验收，后继项才会执行。同一成员可以承担多个独立工作项。
- 成员必须提交可读取的内联正文。自报完成、外部链接和不存在的文件不能单独放行。
- 独立复核读取实际正文，逐条评价并引用原文；失败或缺乏依据不算通过。原文引用并不能证明程序运行正确。
- 要求实际检查的工作项，必须有绑定当前成果版本的本地检查回执。模型不能用 JSON 字段伪造本地检查。
- 明确返工使相关后继失效，不重跑独立分支。规则、方向或计划变化时，旧版本停止放行。
- 调用结果不明或租约超时不自动重放。内置 CLI 在工作项调用中也关闭内部重试；第三方适配器自身的行为仍需审查。
- 未验收或已失效的工作项成果不会进入跨任务成果记忆。历史无工作项绑定的发布成果仍按原有方式读取。

## 执行中对话

在原对话里发送“进度怎么样”“现在做到哪了”或“做完了吗”，店长会读取当前工作项记录回复，不发起模型调用，也不改目标版本。可在前面点名已配置的伙伴，例如“@月亮 进度怎么样？”，仍由店长报告任务整体进展。“继续”请求推进现有计划，不会把已经验收的工作重做一遍。

这里只精确识别少量独立查询和续做语句，不是通用意图理解。混合消息（如“继续，但不要改接口”）、未知表达、显式新目标或新验收标准仍视为要求变更，不会因为含有“继续”就被忽略。真正变更会使旧计划停止放行；配置店长规划通道后，下次执行会重新规划，否则仍需更新本地计划。“继续”不能绕过过期计划或结果不明的检查点。

工作项将该目标版本之前的完整要求记录传给执行者和独立复核人，不再仅依赖最近三条聊天摘要。进度查询和单纯续做不混入要求记录。超过输入容量时停止执行或记录验收延期，不截断约束后假装完成；长历史的分层检索与语义影响分析仍待完善。

运行时会区分尚未发出调用（例如预算不足、熔断或调用前版本变化）和调用发出后结果不明。前者调整条件后可以续做，后者仍必须先核查副作用，不能盲目重放。此判断来自运行时调用边界，不接受驱动自行宣称“没有执行”。

## 本地检查

先在任务详情 API 的 `task.work.items` 中找到工作项和 `local_check` 标准的 ID，再执行明确授权的命令：

```powershell
python -m cater --db .cater/cater.db verify TASK_ID --work-item ITEM_ID --criterion behavior -- python -m unittest discover
python -m cater --db .cater/cater.db run TASK_ID
```

检查命令在该次提交的内联成果临时副本中执行，不在当前工程目录执行。每份成果需要安全且不重名的文件名；当前仅支持单层文件。记录提交摘要、输出摘要、退出码，并检查提交文件是否被改写。检查回执只证明该命令的观察结果，不能外推为完整项目正确。

**临时副本不是操作系统沙箱。** 命令及其子进程仍继承当前用户权限，不应运行不可信程序。不要把模型返回的命令直接传给本地验证入口。工作项执行器本身不会按模型提供的路径读取主机文件。

### 并发检查与重验

本地检查在执行前原子登记，完成回执绑定该次检查和提交版本。同一标准上同时开始的检查形成一个波次：全部结束前不放行，其中任一失败不能被迟到的成功隐藏。只有先前波次全部结束，后续显式检查才记录替代关系。检查期限已过但未收到回执时保留结果不明，不自动重放。

新增检查使旧阶段验收及相关下游失效；下游已经执行中的副作用需要先核对。旧历史没有启动事件的检查可读取，新检查不能用旧回执补齐。检查实际失败时直接返回返工检查点，不再调用模型重复解释失败。

## 整体交付与复查

阶段全部通过后，运行时生成不可变候选清单：绑定工作计划、目标与店规版本、每项提交与验收记录，以及所选正文的哈希和交付路径。配置店长模型后，店长读取全部要求、当前店规和实际正文，核对语义覆盖与成果组合。未配置模型时保留待整体复核，不用演示话术制造完成凭证。

- 每条原始和后续要求均需记录通过、失败、依据不足或被后续要求替代；引用必须来自本次交付正文。替代关系只能引用后续顾客原文，不能替代店规，且最终替代要求仍须通过核对。
- 涉及必需本地检查的工作计划，或实际交付中包含代码正文，还需要整体行为检查；不能利用规划漏写标准绕过该门。阶段回执不能替代整体回执。缺失、失败、在途或结果不明都不放行。模型不能自行声明整体命令已执行。
- 整体复核发现有正文依据的问题时，相关工作及依赖返回返工，下次推进处理它们；证据不足或无效响应停在检查点。已发出但返回不明的复核不会盲目重试。
- 复核结论和下载都核对候选版本。需求、店规、计划、正文或检查发生变化时，旧交付失效；人工完成确认不能绕过这些验收门。
- 人工返工反馈使旧计划与交付失效，并作为后续规划的完整要求保留；复核期间更新检查只淘汰旧审查结论，待新检查结束后可以重验。同一任务不能靠换版本绕过尚未结束或结果不明的整体复核。

需要整体实际检查时，显式执行可信命令，例如：

```powershell
python -m cater --db .cater/cater.db verify TASK_ID --delivery --criterion integration_behavior -- python work-1/check.py
python -m cater --db .cater/cater.db run TASK_ID
```

这是文件路径示例，不是适用于所有任务的验收命令。实际检查标准、命令及覆盖范围必须符合任务。副本按 `work-1/原文件名`、`work-2/原文件名` 等目录保存，避免跨工作项同名覆盖；同一项重名则停止。该布局是各项正文的确定集合，不会自动合并为可运行工程；需要组装的项目应在工作计划中安排实际集成成果及其验证。

整体验收通过后，在原对话和成果板查看交付摘要、关键选择原因、复查步骤和未覆盖范围。下载交付包包含所选正文、`manifest.json` 和 `handoff.md`；后端下载路径为 `GET /api/tasks/TASK_ID/delivery`，沿用工作台访问令牌保护。修改要求后不会继续下载旧版本作为当前正式交付。

**这些门禁证明版本与证据关联，不证明模型判断永远正确。** 原文引用不能证明语义完整，命令退出成功不能证明检查充分；复核还应检查实际命令与观察范围。真实模型质量、多轮复杂工程和交接教学质量仍需要实际任务评测。

## 自定义工作计划

Python 运行时提供 `Runtime.plan_work(task_id, items)`。每项包含 `id`、`owner`、不同于作者的 `reviewer`、`objective`、`depends_on` 和 `criteria`；每条标准包含 `id`、`kind`（`review` 或 `local_check`）与 `text`。计划拒绝重复 ID、缺失前置、自依赖、环及作者自验。`Runtime.collaborate` 运行就绪项并尝试独立审查；不必新增角色来容纳更多工作项。

## 店长规划通道

默认店长仍使用本地规则，不会悄悄调用模型。在自己的 roles JSON 中，为 `organization.leader` 添加 `"driver": "planner"`，并在 drivers JSON 中配置同名 API 或 CLI 通道即可启用。也可以引用一个已经配置的通道名，与其他成员共享账号和已报告用量预算。启动参数仍为 `--roles` 和 `--drivers`；完整接入方法见 [示例说明](../examples/README.md)。

首次执行或要求变更后的执行，会调用店长规划通道。输入包含原始要求、后续变更、店规、可用成员、当前计划和候选成果正文；返回契约见 [`planning-response.schema.json`](../cater/packs/planning-response.schema.json)。现有 API driver 可以接收该提示词；自定义 CLI adapter 需要识别 `context.work.phase == "planning"`，不能始终返回普通聊天对象。仓库中的 Codex adapter 已区分规划、执行和审查契约，但不自动授予执行权限。

- 每条要求必须关联具体工作，或引用后续顾客原文说明替代关系；每项工作必须有来源、执行成员、独立复核人和合法依赖。
- 规划不能删除或改写旧计划中的必需实际检查。需要改变此类检查时，应先明确修订可信工作契约，而不是让模型自动降级。
- 规划输入与安装时的目标、店规及工作计划版本必须一致。并发规划只允许一个调用；迟到的旧计划保留记录但不下发。
- 可沿用同一作者、同一工作项的候选正文，但不能继承旧验收。前置成果的正文、文件名或格式变化时改为重新执行；候选被否决后不会反复重交同一份内容。
- 结构错误或缺少条件时停在检查点，不自动循环调用。补充要求或明确说“继续”后才再次尝试。返回结果不明时不会因“继续”而自动重放；核对后可显式重新请求规划（`dispatch`）。进程中断留下未结束规划时，目前仍需人工核对，没有自动恢复确认入口。

聊天展示规划说明和停止原因；成果面板可展开“要求与安排”和候选来源。**来源引用只证明可追溯，不证明语义完整或计划正确。** 初次规划中的检查充分性、依赖是否符合业务事实，仍需模型评测与独立验收来验证；运行时不会把模型的覆盖声明当作最终交付证明。

## 当前边界

阶段验收不等于整体交付。整体验收与版本绑定下载已接入；任意工程目录的权限隔离、未知副作用自动核对，以及真实模型跨多次重启的长任务评测仍未完成。可选模型规划和整体复核依赖真实模型的语义判断，本地假驱动回归测试不能证明其质量。

新方向仍采用保守失效和候选重验，不会未经重新核对就保留旧通过凭证；细粒度影响分析仍待实现。新执行路径遇到强制仲裁请求时不能以投票替代成果验收，完整的证据驱动仲裁衔接仍在建设。默认演示没有真实模型审查能力，可能停在待验收，而不会伪装已经通过。
