# 对话式协作

工作台连接支持原生工具调用的真实模型后，普通聊天使用消息协作：店长整理目标，向伙伴交代工作；伙伴执行后回报，店长根据成果继续协调、检查或安排修正。规划、咨询与复核按需进行，不要求每次先安装完整工作流。

直接在同一个聊天框补充要求、换方案、确认上一个建议或询问进度，也可以 `@` 伙伴。任务列表沿用现有会话标识，当前工作目标单独记录；换目标不删除旧消息和成果。店长采用新目标后，旧委托不再启动新的操作。

## 接力与回报

每位伙伴都能接收工作，也能向另一位伙伴交代工作或要求复核，不必每一步经过店长。委托文字应交代背景、输入成果、具体要求和验证期待。接收者读实际文件与工具回执后执行，发现问题可以直接交回修正，再检查修正结果。

`delegate` 与普通 `send_message` 都会唤起接收者；宿主不靠消息里的关键词决定工作内容。处理结果自动回报给发件人，子工作回报会带回原委托上下文。显式回答已有问题或交还委托时，`send_message.reply_to` 关联原消息，避免把回报误当新任务，也不会重复补发同一份回报。仅供知悉、等待信息时可安静等待，回执不会无条件互相触发。

只是同步进展、不需要对方回复或行动时，角色可使用 `send_message.notify_only`。知会保留在可展开协作记录和后续上下文中，不计为待办，不单独唤起接收者；它也不代表原工作已完成。角色自行判断是交代工作、交回结果还是仅供知悉，宿主不按发言里的词语猜测。

最近发给当前角色的知会有独立的有限上下文区，不被其他伙伴的聊天直接挤走；更多内容可用 `read_messages` 按序号分页补读。补读不会重新执行历史消息，也不会扩大工作目录权限。正式回报只关联原请求或委托，不把知会的“收到”变成另一轮工作。

每次继续模型工具调用前都会更新当前协作快照，同时保留原生工具历史，避免一轮操作始终停留在开工时的旧状态。上下文明确标识当前身份、发件人和原委托，并列出已发出但尚未收回结果的工作。顾客中途追问导致原调用让位时，不把中断提示当成完成回报而关闭委托。

模型输入使用独立的工作投影，不把公开页面和完整审计反复发送：当前输入、原委托、最新顾客消息、复核要求及反馈保留原文；聊天背景使用明确标注的 UTF-8 字节窗口，旧运行只保留近期索引，成果按文件名给出最新发布版本。需要上下文原文时，角色可用 `read_messages(scope="conversation")` 分页补读同一群的共享对话；默认不传 `scope` 仍只读自己的收件箱。读取不会唤醒其他成员。完整历史、旧文件和审计不因此删除。

较长的本轮工具历史只按完整的“模型请求工具 + 全部工具结果”分组移出发送窗口，保留最近完整交互和旧操作的回执引用，不改写签名内容或假造总结。默认软窗口为 96,000 字节，单组超过时仍完整保留，不能把它理解为 token 或费用上限。需要旧输出可按本轮 `run_id` 读取真实回执；移出窗口不代表允许重放操作，也不代表验证通过。该机制减少重复输入，不能保证模型不再重复检查或费用一定下降。

新的 `team.model_called` 记录保留提供方实际返回的输入、输出及缓存等白名单计数，并另记准备发送的 prompt UTF-8 字节数、历史和工具定义的 JSON 字节数。字节不等于 token，也不是完整 HTTP 请求体积；缓存、推理细项不重复加入总 token。旧记录或提供方没有返回的明细不能事后补算，真实账单仍需按服务商计费口径核对。

“成果与过程”的团队进度直接显示本群累计已报告用量，包括同群的历史目标；桌面在右侧查看，手机沿用原成果面板。展开“成员用量与最近返回”可看各成员合计和最近八条返回，不把几百条用量记录塞进聊天。估算、未报告和未注明来源的历史数值与已报告合计分开；缺少计量不显示成真实零。完整单条记录仍在过程回放中。

用量注明截至事件序号，只统计本群保存的模型返回，不是账号余额或全部请求次数。失败、在途或未返回用量的请求也可能已经计费，页面不能补算。Chat Completions 输入计数包含缓存，Anthropic 的原始输入计数不含缓存创建和读取，明细按各自含义展示，不混加为账单。已报告总量可用、但没有输入输出拆分的旧记录仍会保留在合计中。查看、展开和切换这些记录都不会重新调用模型、恢复暂停任务或改变用量上限。

角色可以在同一轮投递委托并安静等待，减少只为确认“正在等待”而产生的额外调用。如果同轮工具操作失败，会把完整回执交回模型修正，而不是忽略错误进入等待；已经成功的操作不会自动重放。

工作检查点从持久事件重建，保留当前未交还工作的原委托序号、收发双方、最近接续与处理状态；`read_checkpoint` 可分页补读完整原要求，不依赖最近聊天恰好仍在上下文里。原发件人需要接续未完成工作时，可用 `send_message.continue_assignment_seq` 关联原委托，并说明读过现状后的下一步；接收者交回的仍是原委托。已经交回、过期、在途或另有待处理接续的委托不会再被重复接续。

店长默认负责与顾客对接、说明整体进度和确认最终交付。成员的执行结果与复核结论是给委托人的阶段回报，不分别代表整个任务已完成。群内协作按收件人标识并默认折叠，随时可展开查看完整交流与已保存的执行回执。你直接 `@` 一位成员提问时，他可以直接回答，不会因此自动再唤起店长附和；需要更改整体目标或工作安排时，由角色主动同步。

正式交付统一显示为当前有效的店长最终交付，关联本轮完成记录及验证边界。旧版本称为交付记录，默认折叠；同一目标已经交付时不重复登记。后来的一般问答、成员完成了其中一段，都不代表产生了一份新的整体交付。

店长可在 `finish_work.handoff` 按需保存面向顾客的原因、改动、影响、取舍、运行复查步骤及未验证范围；不要求每个简单回复填写模板。引用须关联本次交付文件的真实正文、可信原生工具回执输出或当前复核意见，不能用其他群、同名旧文件或改写的引文代替。说明与文件版本一起冻结；后续可用 `read_delivery` 读取，不需要为了讲解重新分配任务。引用匹配只是来源核对，不等于证明结论正确。详见[交付追问](questions.zh-CN.md)。

## 修复与复核

需要独立复核的成果，由作者用 `request_review` 提交具体版本，指定合适的复核者。复核者读取成果并按风险验证，再用 `record_review` 明确记录通过或需要修复，而不是仅在聊天里说“可以了”。中间管理层不因此变成必经关卡。

收到修复要求后，问题保持未关闭。作者修正、发布新版，承接原复核记录再交回同一复核者；仍有问题就继续反馈与修改，直到复核通过，再由作者交回原委托，店长完成整体交付。即使原本已通过，作者接受建议继续改动文件后，旧结论也不能覆盖不同内容的新版。

店长提前结束会收到具体的未闭环事项，或仍在处理复核意见、尚未交回的相关作者委托，原工作不会因此取消；应继续协调修复，不把错误转成“等待顾客催”。这只核对承诺和成果版本的一致性，不等同于宿主证明模型复核正确，也不要求所有成员都闲下来才能交付。没有复核委托、作者发布完整说明后安静等待的简单任务，店长仍可直接检查交付。

最终交付保存确切的成果序号与内容摘要，下载包使用该版本快照。进度区可查看当前由谁修改、由谁复核及具体反馈。历史记录保留原样，不事后把旧任务改写成已经执行过新流程。

## 对话中的进展

对话工具栏的“任务脉络”可以打开当前群的协作图，查看实际委托、子委托、回报与版本复核，也可切换列表阅读原文和处理状态。连线表示有记录依据的通信关系，不是强制执行顺序；消息处理结束、回报已投递与成果复核通过分别展示。图只读，不会创建旧工作计划、投递新工作或重试失败调用。

消息发出后，输入框上方的“当前工作进展”在原位更新，不随聊天滚走，也不为每次状态变化新增气泡。它分别说明最新消息是否收到、正在由谁处理，以及后台工作是否还在执行；回复结束不等于整个任务完成，旧交付也不代表新的追问已经回答。直接点名成员时显示实际收件人，不假装店长一直在输入。默认只展示两项优先进展，完整内容从“查看过程”进入。

执行工具期间的过程性发言归入可展开过程，减少店长自己的“收到、已安排”连续刷屏。实际答复、正式交付和仅等待信息时的对客发言仍在主对话，避免隐藏真实澄清；过去的记录按可信的同轮工具开始关联兼容展示，不根据发言关键词猜测，也不改写历史事件。

角色与工具动作依据实际运行记录展示，完整交流、执行回执和成果仍在“查看过程”入口。没有时间依据、同步失败或超过一分钟没有新执行反馈时撤下活动动画，显示待确认，而不是编造百分比或私有思维过程。缺少新回执不等于进程已经停止，也不会因此自动重发命令。

后台执行期间仍可继续聊天、保留未发送草稿；“刷新状态”只查询，不启动工作。“暂停后续执行”沿用任务控制，在途调用仍可能返回。任务确认交付且没有未答消息或在途工作后，进展区收起，保留交付答复和成果入口。

只在聊天里写“交给某某”不等于投递成功；实际消息、执行回执与成果分开记录。模型请求失败不等于完成，明确的服务商限流会标明 HTTP 429，不冒充余额不足或工作结束。

## 聊天中的补充信息

支持原生工具调用的角色需要顾客补充信息时，可用 `request_questions` 把相关问题合成一张聊天内的问题卡。每题由模型指定单选或多选，可标记推荐选项；推荐不会自动选中。每题都能自己填写，也可以在选择后补充文字，或明确跳过。不需要跳到另一页，也不需要逐题发送。

选择和填写只改变草稿，整组提交后才作为一条顾客消息交回原提问角色继续处理。切换对话不会清空当前页面中的草稿；失败不自动重发，手动重试沿用同一请求标识。角色在委托中提问时，回答后承接原工作，不把补充信息当成另一份新任务。

可以继续直接聊天，不强制填表。新的自由聊天、目标变化或同角色发出新问题后，尚未回答的旧卡失效，避免用旧选项覆盖新方向；回答一位伙伴的问题不会使另一位伙伴的问题作废。目标已切换时，先前排队的旧表单回答不会再启动旧方案。跳过仅表示没有提供信息，不等于同意推荐、确认假设或授予操作权限。暂停或取消执行时不提交问题卡，仍可普通聊天。

旧的纯文本提问不会被事后猜测转换；结构化卡片来自角色实际调用工具，不是前端按问号识别。旧演示路径的单题澄清入口保持兼容。

## 文件与执行

- 成果发布后保存完整正文，可在成果板打开或下载。文件保存不代表代码已经正确运行。
- 需要读写项目、运行命令时，先在工作台绑定已配置的工作目录及权限。伙伴使用真实工具取得文件、命令输出和验证结果。
- 未绑定工作目录时仍能交流、发布文本成果，但不能把聊天中的代码或自述当作本机运行证据。
- 配置可选浏览器检查器后，原生伙伴可用 `browser_check` 实际操作本群最新已发布的静态网页副本，记录具体断言和文件版本，不需旧工作计划。失败、不可用、超时与历史范围分别保留；通过不等于复核或业务验收自动通过，见[浏览器检查](browser-checks.zh-CN.md)。
- 店长的交付结论会保留实际验证与未验证范围；它是模型判断，不是独立的宿主正确性认证。

成果板区分本轮最新发布、交付时锁定文件和历史版本，不把返工的每一稿平铺成多个当前成果。店长可以明确选择沿用旧文件，不需重新发布未改动依赖；默认不会把旧目标所有文件带入新交付。具体取回范围与版本绑定见[成果文件](artifacts.zh-CN.md)。

角色的上下文提供最近20条轻量回执引用，不重复附上整份命令输出。核查时可用 `read_receipts` 按 `role`（角色ID）、`message_seq`（原输入或委托序号）、`name`（工具名）组合筛选完整结果，或用索引中的真实 `run_id` 精确定位。角色名不是运行ID；传错会得到明确错误，不再静默返回空成功。更多历史可用 `before_seq` 向前翻页。

原生伙伴还会得到有界的工作指引目录，只在需要具体方法时使用 `read_skill` 阅读，或用 `list_skills` 翻页。内置指引覆盖问题溯源、实际检查、版本复核及交付讲解，宿主可额外登记项目 Markdown；读取不是执行、授权或验收，也不是每次开工的必经步骤。正文在可展开过程中按纯文本展示，配置失效不阻断普通工作。详见[按需工作指引](skills.zh-CN.md)。

从已有对话衍生的新群还提供冻结背景索引。角色可用 `read_background` 读取 `index` 引用列表、`goal` 来源目标、`source` 顾客原文或 `artifact` 文件正文；正文使用字符偏移分页，不读取来源群后来的消息或文件版本。该工具只在有继承背景的群里提供，暂停时也能用于只读讲解。历史材料不是当前任务要求、权限或通过验收的凭证，详见[衍生对话](conversations.zh-CN.md)。

回执保留完整失败输出，且只来自当前对话。历史测试通过不证明文件此后没有变化，也不证明所有场景正确；由复核者结合实际修改与风险决定复用哪些证据、补做哪些检查，而不是每一层机械地重跑或一概免检。

角色还会收到未结算操作的轻量索引，可用 `read_receipts` 的 `include_pending` 分页读取详情。纯本地的委托、消息、目标更新、问卷、复核与交付事件现在与对应回执原子提交；只有带该版本执行契约且原运行已结束的未结算操作，才能说明本地事件未提交。旧记录、文件发布与命令执行不能据此推断没有发生，仍须核对实际影响。索引不是重放授权，也不会自动重新领取原消息或恢复模型历史。

## 中途消息与暂停

执行者在模型调用之间交回调度，新顾客消息优先于下一份未开始的委托。已经发出的模型请求或命令不会因聊天瞬间终止；新的目标在后续操作边界生效，不承诺硬实时中断。

暂停后仍可询问状态和阅读成果，不会因此恢复文件写入或命令执行。伙伴间待处理消息保留在队列，恢复后再处理，不在暂停时消耗掉工作委托。暂停恢复需要明确操作。新契约下的进程中断可以通知店长核对后续作，内部通知默认折叠；它不重发旧请求、不绕过原委托和复核，也不把未知工具结果变成成功。具体范围见[暂停与故障恢复](recovery.zh-CN.md)。

## 兼容范围

支持工具调用的真实通道，网页普通新建、续聊及衍生对话默认使用消息协作，不依赖浏览器发送 `collaboration: "team"`。显式治理、旧结构化指派入口仍保留原语义；本地演示仍走原演示路径，不冒充自主执行。历史消息与成果不改写；闲置旧群在下一条普通消息时可切换，旧协作仍在途时不能同时切换引擎。原创建请求重试返回原会话，不借重试悄悄改换引擎。

第一版仍有上下文窗口与单轮执行资源边界，没有承诺任意长度任务永不出错。内阁投票不是默认关卡；持续共享会话、跨群协作、复杂任务资源调度还需要分别验证。
