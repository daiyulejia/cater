# 对话式协作

工作台连接支持原生工具调用的真实模型后，普通聊天使用消息协作：店长整理目标，向伙伴交代工作；伙伴执行后回报，店长根据成果继续协调、检查或安排修正。规划、咨询与复核按需进行，不要求每次先安装完整工作流。

直接在同一个聊天框补充要求、换方案、确认上一个建议或询问进度，也可以 `@` 伙伴。任务列表沿用现有会话标识，当前工作目标单独记录；换目标不删除旧消息和成果。店长采用新目标后，旧委托不再启动新的操作。

店长应区分原工作内的反馈与真正换目标：尚未交付时，修复原需求中的缺陷或调整实现做法，继续原委托和版本复核；只有更换交付目标、或已交付后开始新工作时才使用 `set_objective`。该工具不是进度更新器：不同目标文本会切换工作版本，旧委托与复核不再适用，但已执行操作不会撤销。这是提供给模型的语义指引，不是关键词路由，也不保证模型每次判断正确。

输入框按 Enter 发送，Shift+Enter 换行；中文输入法选字时不会发送。展开 `@` 候选时，Enter 优先选择成员，不会把尚未写完的消息发出去。

受管外部客户端，以及内置 OpenAI 兼容和 Anthropic API 驱动等待响应时，可以在同一群中轮转处理其他角色的消息；普通追问不必等当前猫咪整轮结束，也不会自动取消它。调度限制在途角色数量并为顾客消息保留机会，不用固定关键词替模型决定该说什么。采用新目标后，旧角色的后续工具仍须核对范围；其他角色尚未停止或尚有未知操作时，不能提前最终交付。

这不代表所有操作均可实时抢占：模型自身响应、同步工具执行、进程启动与清理仍可能等待；仅支持同步执行入口的自定义驱动仍按原方式运行。暂停和本地进程清理也不保证远端已停止推理或计费。

内置 API 的网络等待使用每次调用独有的受管进程，不让子进程访问会话数据库或执行模型工具；这只是生命周期管理，不是操作系统沙箱。公开 `tool_turn` 同步接口，以及被调用方替换或包装过的同步实现，保持原执行方式。完整响应已收到后先记录其可用用量，再核对当前范围；旧目标的文本和动作不能因此落地。中途断开且没有完整用量时，费用仍未知，不自动重试。

伙伴解释已有工作时，可以在 `reply_to_customer` 中按需附 `evidence`：最多8段原工具完成回执的 `source_seq` 与逐字 `quote`，不必每句话都引用。当前支持工作目录读写、运行、目录与搜索、网页检查和成果读取回执；引用必须来自同群既有记录，不能用消息或未结算操作代替。原文不可得、摘录不符或可选引用格式无效时，整组引用不保存、不展示，正文仍只发送一次；既有折叠详情提示引用未保存，不代表正文已经验证。不会为修饰引用重新派活或自动增加模型调用，不能借此跳过正文、身份、权限与当前工作范围检查。

主对话保持简明，依据默认折叠在“查看答复依据”中，显示原始摘录和当时的工具状态、退出码、采集完整性。失败命令也能引用；输出片段中有“OK”不代表整条命令成功，伙伴的解释或复核也不是宿主认证。引文仅证明这段文字存在，不证明测试身份、覆盖率、原因推断或当前文件状态。没有附引用的旧消息保持原样，历史读取不扩大执行权限。

被省略的引用以宿主工具回执中的 `reply_evidence_status: "omitted_invalid"` 和固定提示记录，不把部分有效引文混成一份通过的证据。答复、原调用和回执配对保存，重启后不会因为引用被省略而重发已回答的问题；已有委托、未知操作与任务完成状态不因此改变。省略是当时的宿主决定，来源后来恢复可读不会悄悄升级旧答复的引用；相同请求重试返回原回执。历史上只有引用失败回执、没有实际答复的输入仍按原恢复流程处理，不补造已发送消息。

## 交付说明

`finish_work.summary` 是顾客看到的最终答复，不是内部工作小结。按任务先给可用成果或实际答案、最短操作，以及影响使用或判断的关键原因与风险；即使中途已经说过，最终也收束必要结论、数字及口径，让顾客不展开记录也能知道结果和下一步。咨询、文字成果与工程交付按任务自然表达，不要求都写成工程验收报告。

长证据、事件编号、逐文件改动、详细复查步骤及非关键取舍，可以放在可选的 `handoff` 中，从已有“为什么这样做·如何运行”入口展开；主摘要不重复整份说明，关键边界也不只藏在折叠里。需要复查时给实际目录、条件、完整命令与预期结果。顾客要求全文、完整报告或精确数字时，应保留所求内容，不因分层省略。

说明依据实际记录区分输入方式、执行者、环境与未验证范围。例如 `-c` 命令和 stdin 脚本分别归因，作者执行、伙伴复核与后来独立补验分别说明；宿主隔离环境通过不等于顾客终端实测。有限样例不证明全兼容，顶层字典也不自动限定所有嵌套值；未验证某种对象或环境，不等于顾客明确排除它。

需要附依据时，店长可按需调用 `read_handoff_sources`，从实际成果、当前目标回执和版本复核意见中选片段；在 `handoff.evidence` 中填写 `{"evidence_id": "返回的编号"}` 即可，宿主重新核对并保存原文与来源哈希。旧的 `source_seq` 加逐字 `quote` 仍可使用。引用编号是片段选择，不是批准或权限；换目标或改变最终所选成果后，原编号可能失效，需要按实际版本重新读取。

外部 Qoder 通道可显式选择 `tool_surface: "catalog"`，通过固定的目录与调用入口使用同一批实际授权工具；默认 `all` 不变。目录是本轮定义快照，不是最新授权证明；读取不产生工程执行或验收回执，也不续延有效进展计时。实际调用仍以原工具名、参数、结果及回执记录，复核、交回、交付成功后仍让出执行。暂停、范围变化和未知影响不会因目录入口绕过。该模式不等于动态工具注册，也不保证比默认模式便宜或更快。

工作上下文的回执索引可附少量 `command_record`，区分宿主收到的工具请求与记录中的实际 `argv`、目录和环境，不复制日志或标准输入正文。省略项可将自身 `seq` 作为 `receipt_seq` 交给 `read_receipts` 读取原完成结果；该回读不含原工具请求，不能从 `argv` 倒推。索引只描述当时的调用，不证明当前文件未变、测试覆盖完整或顾客终端能够直接运行同一命令，也不自动重跑。

`read_receipts` 的已知输入错误会给出具体字段和固定修正说明，允许模型在同轮修正，不自动改参或重新执行。精确的 `receipt_seq` 不与 `include_pending: true` 合用；未结算操作另用分页查询。`section: "file_reads"` 只读文件来源元数据，不填写 `receipt_seq` 或 `include_pending`。输入被拒绝不表示原操作失败、停止或可以重放；存储和执行异常也不会伪装成可纠正参数错误。

`artifact_seqs` 可明确指定拟交付文件，省略时列当前目标的最新成果。来源按事件倒序，每页至多六项，用 `before_seq` 继续，或用 `source_seq` 精确读取；同一来源至多四个片段，每个片段至多512个UTF-8字节，截断有标记。需要更完整上下文时仍应读原文件或回执。普通工具的完成编号不保证适用于交付引用，尤其不能把消息交回或读取动作当作代码检查通过。该读取在暂停时也可用，不执行原操作，也不登记复核或交付。

需要保留实际工程命令时，可在 `handoff.command_receipts` 中选择至多四个本群当前目标的 `workspace_run` 完成回执 `seq`，先用 `read_receipts` 核对编号，不使用客户端调用标识。宿主冻结来源事件、已记录的工具请求、原环境程序参数、目录关系、结果和输出节选；从原有交付说明入口展开“实际命令记录”，与“成员建议的运行与复查”分开，下载说明也保留这些记录。引用失败命令不会把它变成成功，查看和复制不会重新执行。

工具请求是 Cater JSON，不是终端命令行参数；原环境的程序路径也不承诺可在其他机器直接运行。工程授权/锁根不等于外部客户端目录，成果副本模式的 `cwd` 相对已清理的临时副本根，不能拼接成原工程内的运行路径。未绑定成果版本的普通工程命令不证明后来交付的 ZIP 已检查。

请求和程序参数各最多保留 1,024 个 UTF-8 字节，超出时整项省略，不伪造截断命令。stdin 仅保留配置输入的字节数及摘要，不复制正文，也不证明程序读取过；未知请求字段不会复制，省略项会使请求标为不完整。输出各只保留已保存开头的至多 512 个 UTF-8 字节，明确标记截断，不补成全文或末尾。完整说明含这些宿主信息仍受 24 KB 限制。这个可选引用不是密钥通道，原命令参数或输出中的敏感业务文字仍应按实际交付范围谨慎选择；无此字段的旧交付保持原样。

这些是表达与核对指引，不是内容审判器。没有新增必填字段、固定字数或关键词门槛，也不自动裁切、改写答复或增加模型调用。简单文字答复可以不带 `handoff`，阅读技能不是交付前置条件；说明的类型、大小及逐字引用仍严格校验。引用无效但正文合法时，保留净正文、移除全部引用与命令记录，标记 `references_omitted_invalid`，读取、折叠详情及 ZIP 内说明均提示“讲解已保留，引用核对失败未保存，不视为验证证据”；正文格式或大小不合法时仍整份不保存，主要成果与结论保留，不自动增加模型调用重试说明。`verification` 保留实际取得的验证结果和范围，说明本身不执行命令，也不等于宿主认证正确。

## 删除对话

在对话右上角的“更多任务操作”中选择“删除对话”，核对后从会话列表持久移除，并取消后续工作。已经发出的调用仍可能返回，这不是强制终止远端执行或停止计费的保证。刷新、重启或旧响应返回不会把已移除对话重新加入列表。

目前采用逻辑移除，不提供隐私擦除：聊天、成果与审计链仍保留在本机数据库中，已落盘的工程文件也不会删除。原始回放和冻结衍生背景继续保留来源依据；已移除对话不再接收新的网页操作。需要清除本机数据时，应另行备份并处理数据库与文件，不把列表移除当成数据已销毁。

## 接力与回报

每位伙伴都能接收工作，也能向另一位伙伴交代工作或要求复核，不必每一步经过店长。委托文字应交代背景、输入成果、具体要求和验证期待。接收者读实际文件与工具回执后执行，发现问题可以直接交回修正，再检查修正结果。

`delegate` 与普通 `send_message` 都会唤起接收者；宿主不靠消息里的关键词决定工作内容。伙伴通过工具向发件人交回结果，子工作回报会带回原委托上下文。交回当前负责的工作时，角色可用 `return_work(text)`，由宿主关联本轮原委托及原发件人，不必重抄编号和收件人；没有明确原委托时不会猜选其他未完工作。`send_message.reply_to` 仍兼容显式交还指定原消息，两者复用相同身份、目标版本、撤回和已交回检查，不重复补发相同回报。

`return_work` 交回的是阶段结果、证据与未完事项，不代表整个目标完成或独立复核通过。正式复核仍用 `record_review`，店长最终交付仍用 `finish_work`；仅同步进展用知会，不提前交回。待判定的正式复核若使用普通交回，宿主不会投递假成功，而会返回对应复核序号及登记结论的入口，允许同轮纠正。回执与原消息关联后，既有协作记录和图可显示“交回当前工作”，不用额外操作入口。普通问答或仅供知悉时可直接答复、安静等待，不无条件互相触发。

正式交回当前原委托成功后，原生 API 与外部客户端都会结束本轮，不再执行同批后续动作或仅为收尾增加模型调用。交回失败、只发知会或与原委托无关的消息不触发这个结束；后续收到新的工作仍可继续。这是交接的执行边界，不表示整个目标已验收或交付。

如果当前模型输入已完整包含这份委托的下游回报，角色随后显式交回上游，宿主会把尚未领取的这份回报一起标记为已处理，避免再次唤醒同一角色。原消息仍保留可读；截断、未呈现、迟到及其他工作的消息不会因此消失。该记录与交回同事务保存，失败时一起回滚，也不把复核的“需要修改”变成通过。外部客户端只确认启动时完整呈现的回报；旧交回记录不追溯补记。

同一批工具中先有错误、随后成功提交复核或登记结论，也会让出本轮执行；先前错误回执保留，不因一次可纠正错误继续操作已经交接的成果。复核版本已变化时须由原送审负责人取得新版并续提，不能用普通回报或旧结论完成验收。

问卷答案或尚未处理的续答可以带回原委托；答案已经处理后，新的普通点名问答不自动当成该委托的结果。未完成工作仍保留在角色上下文，由角色理解是否继续、补充或正式交回，不能因回答选项含义就默认为原工作完成。

只是同步进展、不需要对方回复或行动时，角色可使用 `send_message.notify_only`。知会保留在可展开协作记录和后续上下文中，不计为待办，不单独唤起接收者；它也不代表原工作已完成。角色自行判断是交代工作、交回结果还是仅供知悉，宿主不按发言里的词语猜测。

最近发给当前角色的知会有独立的有限上下文区，不被其他伙伴的聊天直接挤走；更多内容可用 `read_messages` 按序号分页补读。补读不会重新执行历史消息，也不会扩大工作目录权限。正式回报只关联原请求或委托，不把知会的“收到”变成另一轮工作。

每次继续模型工具调用前都会更新当前协作快照，同时保留原生工具历史，避免一轮操作始终停留在开工时的旧状态。上下文明确标识当前身份、发件人和原委托，并列出已发出但尚未收回结果的工作。顾客中途追问导致原调用让位时，不把中断提示当成完成回报而关闭委托。

正常达到单轮工具交互边界不等于任务完成。有原委托的伙伴向委托人交回进展；没有实际上游的根输入会在保存结束记录时，原子记录一次新的店长监督输入。店长从当前目标、成果和回执重新核对剩余工作，不重放旧请求或旧原生历史，也不因此跳过返工与独立复核。若本轮已经由同一运行实际登记交付或正式交回原委托，则不再误报分段中断；交回子工作不等于整个目标已交付。

这类通知使用 `recovery`，以 `trigger: turn_boundary` 区分正常分段与进程丢失。它绑定原输入、运行、结束记录和最后有效输入范围，收尾时不自动采用刚发生的外部规则、控制或工程变化。监督执行持续核对范围，只允许本运行已记录的目标采用或交付推进版本；已失效响应不会继续派活或写文件。新的顾客消息会接管旧分段通知，暂停或取消不会被通知解除。监督输入自身再次到达边界不会递归自唤醒，也不能绕过配置的通道用量上限；这不是无限续跑或费用改善的保证。已有普通失败、旧中断和人工暂停记录不会被批量升级成自动重试。

一次请求的数据库消息、目标、委托、工程绑定、店规与工具范围来自同一读快照；发请求前再核对顾客新消息、目标、暂停及工程范围。检查发现这些变化时，不再用旧上下文启动请求；检查之后仍可能发生并发变化，已经发出的请求也不能瞬间撤回。读事务不跨模型调用或工具执行。外部配置文件不是 SQLite 快照的一部分，执行时仍会核对当前权限和指纹。

店规采用记录保存该快照看到的确切正文，记录顺序不代表规则生效顺序，也不能单独证明模型请求已发出。原生模型返回或失败记录中的 `context_basis` 关联全局数据库截点和店规记录，供核对当时输入，不保存另一份提示词或私有推理。群内工作检查点的 `as_of_seq` 仍表示本群最后事件，不能代替包含共享规则等事实的全局截点。

模型输入使用独立的工作投影，不把公开页面和完整审计反复发送：当前输入、原委托、最新顾客消息、复核要求及反馈保留原文；聊天背景使用明确标注的 UTF-8 字节窗口，旧运行只保留近期索引，成果按文件名给出最新发布版本。需要上下文原文时，角色可用 `read_messages(scope="conversation")` 分页补读同一群的共享对话；默认不传 `scope` 仍只读自己的收件箱。读取不会唤醒其他成员。完整历史、旧文件和审计不因此删除。

完全相同来源的正文可只在本次模型输入中保存一份，其余字段保留来源标识，以 `text: null`、`context_ref: "message"` 这样的形式引用同轮同名字段的完整 `text`；允许的来源为 `message`、`active_assignment`、`latest_customer_message`，引用只一跳，不跨轮。`null` 不代表要求为空，也不代表旧工作完成；不同来源、正文或冲突视图不会合并。只有连同说明后的整体 JSON 字节更少才使用，短输入不为新引用增加开销；原始事件与公开页面保持完整正文。这不是 token、缓存命中或费用改善的保证。

较长的本轮工具历史只按完整的“模型请求工具 + 全部工具结果”分组移出发送窗口，保留最近完整交互和旧操作的回执引用，不改写签名内容或假造总结。默认软窗口为 96,000 字节，单组超过时仍完整保留，不能把它理解为 token 或费用上限。需要旧输出可按本轮 `run_id` 读取真实回执；移出窗口不代表允许重放操作，也不代表验证通过。该机制减少重复输入，不能保证模型不再重复检查或费用一定下降。

新组装的模型上下文和原生宿主工具结果使用紧凑 JSON，仅去掉字段、数组元素之间的格式空格；正文中的空格、换行、源码、字段值及顺序保持不变，不削减角色身份、要求、权限或复核依据。已有模型回复和签名历史不重新格式化，持久化记录、成果文件及审计摘要不因此改写。原有历史软窗口不变，结果缩小也可能多保留一组完整交互，因此总输入不保证每轮变小。减少的字节不等于省下的 token 或费用，也不能解决不必要的模型调用。

新的 `team.model_called` 记录保留提供方实际返回的输入、输出及缓存等白名单计数，并另记准备发送的 prompt UTF-8 字节数、历史和工具定义的 JSON 字节数。`request_sizes.instructions_utf8_bytes` 和 `context_json_bytes` 分别记录完整说明与本轮上下文文本的字节数，两者之和为 `prompt_utf8_bytes`；这些大小字段不包含原始输入或私有思考。外部客户端记录的是宿主交出的提示文本，不包括客户端自行补充的内容。字节不等于 token，也不是完整 HTTP 请求体积；缓存、推理细项不重复加入总 token。旧记录或提供方没有返回的明细不能事后补算，真实账单仍需按服务商计费口径核对。

原生 API 可显式选配 `tool_loading: "on_demand"`，默认仍为 `"all"`。开启后，聊天、交接、交付、工作指引和回执工具常驻，其余可用名称在 `tool_catalog` 中列出；角色可一次调用 `load_tools(names=[...])` 选择多项，下一次请求才提供这些工具的完整原始定义。加载只确认名称，不执行动作、不扩大权限，也不把定义再复制进工具结果。正式复核者从首轮就能登记复核结论，不必为此多一次发现请求。已加载定义在同一次成员运行内保留，避免旧工具历史失效；新运行重新选择，历史与成果不删除。

这是一种减少重复定义的可选方式，不根据顾客关键词分类任务，也不强制加载全套能力。当前角色、工程绑定、暂停和权限仍决定可用目录，Skill 的可发现性不会因尚未加载某个工具而消失。同一响应不能一边加载、一边使用本轮尚未声明的工具；整条响应先校验，不部分执行。加载占用正常模型轮次，可能增加请求，不能保证每个任务更快、更便宜；`tools_json_bytes` 记录实际声明集合的大小，不等于计费 token。外部 ACP 客户端保持原有固定工具列表，不受这个原生 API 选项影响。该模式仍需真实任务验证，不应仅凭脚本协议测试就宣称交付可靠或费用降低。

内置原生工具 API 已收到无歧义 JSON 对象、但响应结构解析失败时，也保留其中可用的白名单用量，并标记 `response_status: "protocol_error"`。这仅是计量回执：本轮仍报格式错误，不采用其中的文字或工具，也不会自动重试。缺失或无效的用量仍为未知；HTTP 错误、传输失败、非法或歧义 JSON 不能据此补算消耗。现有用量详情会区分格式错误返回，不把记账成功当作工作成功。

工具请求未通过校验时，新的记录还会区分参数 JSON 无效、参数不是对象、请求了本轮未提供的工具、调用标识重复等具体检查结果。店长反馈和既有进展、用量与事件详情使用相同的安全类别，不保存原始响应或私有推理。这些类别只说明哪项检查失败，不等于证明错误来自模型、服务商或接入实现；旧记录缺少类别时保持未知，不事后猜测补写。诊断不会扩大工具权限或执行批次中部分有效请求；格式纠正另按下述设置处理。

原生工具 API 默认每次成员运行最多允许一次格式纠正，可在对应驱动配置中设置 `tool_response_corrections: 0` 关闭（默认 `1`，只接受整数 `0` 或 `1`）。只有解析器确认整条响应的工具均未执行、且属于已知工具请求格式失败时才适用。模型保留先前成功的历史和回执，只收到固定类别与纠正要求，不把非法响应塞回工具历史或重做已成功操作。

纠正占用正常运行轮次并产生一次新的模型调用，两个响应的可用用量分别入账；现有通道用量上限、顾客新消息、暂停、目标、店规与工程权限仍会核对。存在未知操作影响、范围已变化、网络异常、输出截断，或第二次格式失败时不会递归纠正。安排事件只表示准备纠正，关联回执也不等于工具已执行、任务已交付或免费。新运行不自动重放旧的非法响应，旧失败任务不会因升级批量重启。

“成果与过程”的团队进度直接显示本群累计已报告用量，包括同群的历史目标；桌面在右侧查看，手机沿用原成果面板。展开“成员用量与最近返回”可看各成员合计和最近八条返回，不把几百条用量记录塞进聊天。估算、未报告和未注明来源的历史数值与已报告合计分开；缺少计量不显示成真实零。完整单条记录仍在过程回放中。

用量注明截至事件序号，只统计本群保存的模型返回，不是账号余额或全部请求次数。失败、在途或未返回用量的请求也可能已经计费，页面不能补算。Chat Completions 输入计数包含缓存，Anthropic 的原始输入计数不含缓存创建和读取，明细按各自含义展示，不混加为账单。已报告总量可用、但没有输入输出拆分的旧记录仍会保留在合计中。查看、展开和切换这些记录都不会重新调用模型、恢复暂停任务或改变用量上限。

“今天在店里”的营业状态来自当前服务的近期通道观察，不是账号余额或任务验收。原生 API 正常返回后，共用该通道的伙伴可显示营业；请求失败、响应格式无效或输出不完整后，改为待确认，不沿用旧的成功状态。自定义驱动的返回值还需具备宿主使用的基本数据字段，才会记录成功；动态属性不会为健康检查提前求值，自定义元数据映射也不额外读取，无法静态核对时不补造新观察。这些返回仍由原宿主处理，不因此新增执行限制。此核对只影响健康观察，不新增工具执行门禁或改写原计量。正式调用后来恢复时也会更新，不需为了刷新状态另发模型探针。暂停、预算预检、顾客改方向及本机工具失败本身不会被记成通道失败；缺凭据、用量保护和既有熔断状态仍优先。观察五分钟后过期，重启服务不会用历史成功冒充当前在线；打开伙伴页或刷新只读取状态，不调用模型。

角色可以在同一轮投递委托并安静等待，减少只为确认“正在等待”而产生的额外调用。如果同轮工具操作失败，会把完整回执交回模型修正，而不是忽略错误进入等待；已经成功的操作不会自动重放。

工作检查点从持久事件重建，保留当前未交还工作的原委托序号、收发双方、最近接续与处理状态；`read_checkpoint` 可分页补读完整原要求，不依赖最近聊天恰好仍在上下文里。原发件人可用 `continue_work(assignment_seq, instruction)` 选择原委托、说明核对现状后的下一步；宿主从真实原委托取得接收者，补充同一份工作，不新建一份委托。原 `send_message.continue_assignment_seq` 仍兼容，两者复用相同身份、目标与在途检查；接收者交回的仍是原委托。已经交回、撤回、过期、在途或另有待处理接续的委托不会再被重复接续。普通消息不因提到旧工作就自动归并；入口明确也不保证模型总能选对，不代表重放未知操作、批准成果或完成目标。

派活者的工作列表也沿用原委托身份，显示最近一次接续的处理状态，不把旧失败误当成伙伴尚未继续。历史运行记录仍保留；排队、执行、等待或单次运行结束都不等于已正式交回，中断后尚未交还的工作仍需核对。

店长默认负责与顾客对接、说明整体进度和确认最终交付。成员的执行结果与复核结论是给委托人的阶段回报，不分别代表整个任务已完成。群内协作按收件人标识并默认折叠，随时可展开查看完整交流与已保存的执行回执。你直接 `@` 一位成员提问时，他可以直接回答，不会因此自动再唤起店长附和；需要更改整体目标或工作安排时，由角色主动同步。

正式交付统一显示为当前有效的店长最终交付，关联本轮完成记录及验证边界。旧版本称为交付记录，默认折叠；同一目标已经交付时不重复登记。后来的一般问答、成员完成了其中一段，都不代表产生了一份新的整体交付。

店长可在 `finish_work.handoff` 按需保存面向顾客的原因、改动、影响、取舍、运行复查步骤及未验证范围；不要求每个简单回复填写模板。引用须关联本次交付文件的真实正文、可信原生工具回执输出或当前复核意见，不能用其他群、同名旧文件或改写的引文代替。说明与文件版本一起冻结；后续可用 `read_delivery` 读取，不需要为了讲解重新分配任务。引用匹配只是来源核对，不等于证明结论正确。详见[交付追问](questions.zh-CN.md)。

可选说明未通过校验时，完成事件与工具结果标记 `handoff_status: "omitted_invalid"`，附固定的 `handoff_warning`，不复制未验证引文、原始诊断或来源正文。角色仍应先读取原文再作解释；省略说明不会补造理由、命令回执或验证结果。这只改变可选说明的处理：尚未交回的委托、待处理操作、未闭环复核及交付版本不匹配，仍阻止正式交付。

## 修复与复核

需要独立复核时，伙伴或店长可用 `request_review` 直接提交已发布的具体版本，也可把多位伙伴的成果合在同一份复核中，不必让发布者再上线送审或重新发布。首次提交者是该链的送审负责人，负责收取意见、协调修复；指定的复核者不能是负责人或本版任一发布者。复核者读取成果并按风险验证，再用 `record_review` 明确记录通过或需要修复，而不是仅在聊天里说“可以了”。中间管理层不因此变成必经关卡。

新请求以 `owner` 记录负责人、`publishers` 记录每次提交的实际发布者；`author` 保留为负责人的历史字段别名，不表示代码原创者。旧记录不重写，缺少 `owner` 时沿用旧 `author` 的链责任。发布者仍按真实成果来源保存，不因协调者送审而变成协调者创作。

原生复核者仅以普通文字结束、而本次精确版本仍待登记时，宿主会在原运行内提供至多一次补登记提醒，保留已经成功的工具历史，不重发成果或新建复核。提醒按正式请求持久去重，占原运行轮次并遵守用量、暂停、新消息和未知操作影响检查；它只提供继续核查、登记或提问的机会，不选择结论，也不保证后续请求已发出。仍未登记时，原复核委托保留为未完成，不凭文字生成批准。外部客户端不会因此自动重新调用。错误角色代登记会得到指定复核者及原请求编号的明确反馈，仍不能代签。

收到修复要求后，问题保持未关闭。负责人可以自己修复，也可安排伙伴修正；取得新版后由原负责人承接原复核记录，再交回同一复核者。仍有问题就继续反馈与修改，直到复核通过，再收齐相关工作回报，由店长完成整体交付。即使原本已通过，接受建议继续改动文件后，旧结论也不能覆盖不同内容的新版。

同链修订允许合理改名、增补、拆分或合并成果。`artifact_seqs` 表示本轮完整的提交集合，不是仅列改动文件；复核者会收到前后两次的确切成果引用，并对照原目标与历史反馈判断是否遗漏，文件名相同不等于内容完整。`read_checkpoint(review_seq=旧请求号)` 可只读查看历史反馈，已被替代的请求标为 `superseded` 并给出当前请求号，不能继续用旧号登记批准。

同一复核链提交新版后，旧版实际复核委托及其接续、进展和反馈只保留为历史，不再要求额外交回旧版，也不会重新启动旧版检查。新版仍需独立复核，发布者仍需交回实际承担的原开发委托，不能因换了送审负责人就漏掉收尾；更换发布者也不表示历史发布者的原工作已交回或撤回。旧版执行留下的未知命令或外部调用仍须核对，不因换版自动解除；普通委托不会因为文字里提到复核而被关闭。

交回接续工作时，`send_message.reply_to` 可填写原委托号或当前接续消息号。宿主核对同群、双方身份和目标版本后，将回报归回同一原委托，回执用 `resolved_reply_to` 标明归并结果，不另建一份工作。原委托已有相同正文的回报时，返回原回报号及 `already_reported=true`，不重复唤醒上游；不同正文会明确提示原委托已交回、此次未发送，伙伴可核对后另行补充或更正。目标变化或正式复核已被新版替代时，不沿用旧接续交回。

伙伴可以在处理其他输入时，正式交回自己收到的另一份当前委托；该委托及其合法排队接续不必再单独启动一次才能被认可。真正仍在执行的作者、另一份未交回工作及尚未处理的复核反馈，仍分别核对，不因一次回报全部关闭。

原发件人或店长确认一份普通工作已经重复或不再需要时，可用 `withdraw_work` 指定原消息号并写明原因。系统记录“已撤回”，停止后续接单与工具动作，不把它记成“已完成”或替接收者编造回报；原消息、已发生的运行与撤回原因保留。撤回仅针对指定工作，不自动撤销子任务，不处理顾客输入，也不能代替当前正式复核。已启动命令或外部调用的未知影响仍须核对，不因撤回解除交付检查。

独立子任务仍可执行并交回，但其反馈不再唤起已经撤回的父工作；已通过子回报接续父工作的运行，也会在后续工具边界停止。撤回子任务本身不等于父任务已经完成。

派活者在处理反馈时，若本轮自行撤回了已经不需要的原委托，可以继续协调剩余工作、提交复核或整理交付，不会因自己的撤回动作连带中断。此例外只适用于当时已启动的反馈处理；不会重新唤醒旧反馈，也不能保活已撤回的父工作或被新版替代的正式复核。

`reply_to` 用于回应对方发给自己的工作，不能回复自己发出的请求来替收件人确认。方向错误时回执明确给出本群的发件人、收件人和当前角色，便于纠正；跟进自己发出的工作应使用 `continue_assignment_seq`，确实不再需要则明确撤回。

店长提前结束会收到具体的未闭环事项，或仍在处理复核意见、尚未交回的相关作者委托，原工作不会因此取消；应继续协调修复，不把错误转成“等待顾客催”。这只核对承诺和成果版本的一致性，不等同于宿主证明模型复核正确，也不要求所有成员都闲下来才能交付。没有复核委托、作者发布完整说明后安静等待的简单任务，店长仍可直接检查交付。

最终交付保存确切的成果序号与内容摘要，下载包使用该版本快照。进度区可查看当前由谁修改、由谁复核及具体反馈。历史记录保留原样，不事后把旧任务改写成已经执行过新流程。

同链最新提交通过且仍有效后，默认交付不再夹带该链已替代的草稿；其它当前独立复核仍使用的成果不因此排除。显式选中已替代稿会收到版本不匹配提示，不静默换文件，也不删除旧成果。确需重新沿用旧稿时，应将它明确纳入新的提交并再次复核。

## 对话中的进展

任务列表显示目标、当前状态和未发送草稿提示，不用交流条数表示进度。完整消息与折叠协作记录仍保留。成果面板的完整目标和最近工作备注可分别展开，不把普通工作备注当作交付结论。

对话工具栏的“任务脉络”图标可以打开当前群的协作图，查看实际委托、子委托、回报与版本复核，也可切换列表阅读原文和处理状态。连线表示有记录依据的通信关系，不是强制执行顺序；消息处理结束、回报已投递与成果复核通过分别展示。图只读，不会创建旧工作计划、投递新工作或重试失败调用。

消息发出后，输入框上方的“当前工作进展”在原位更新，不随聊天滚走，也不为每次状态变化新增气泡。它分别说明最新消息是否收到、正在由谁处理，以及后台工作是否还在执行；回复结束不等于整个任务完成，旧交付也不代表新的追问已经回答。直接点名成员时显示实际收件人，不假装店长一直在输入。默认只展示两项优先进展，完整内容从“查看过程”进入。

执行工具期间的过程性发言归入可展开过程，减少店长自己的“收到、已安排”连续刷屏。实际答复、正式交付和仅等待信息时的对客发言仍在主对话，避免隐藏真实澄清；过去的记录按可信的同轮工具开始关联兼容展示，不根据发言关键词猜测，也不改写历史事件。

角色与工具动作依据实际运行记录展示，完整交流、执行回执和成果仍在“查看过程”入口。支持公开更新的外部客户端会在本轮结束前显示可展开“工作说明”，标明成员自述；工具动作与执行回执仍单独展示。只保留当前活动各运行最近4,000字符的公开文本，暂停、换目标、结束或实例变化后撤下；片段不进入历史、共享记忆或下一轮模型上下文，私有推理不采集。角色结束时既有最终公开记录按原方式保留。

没有时间依据、同步失败或超过一分钟没有新活动反馈时撤下活动动画与公开片段，显示待确认。年龄同时计入服务端观察间隔和浏览器请求往返等待，重复渲染不会刷新旧片段。公开文字仅说明收到成员反馈，不证明工具已经运行或工作完成；缺少新反馈也不等于进程停止，不会因此自动重发命令。

后台执行期间仍可继续聊天、保留未发送草稿；“刷新状态”只查询，不启动工作。“暂停后续执行”沿用任务控制，在途调用仍可能返回。任务确认交付且没有未答消息或在途工作后，进展区收起，保留交付答复和成果入口。

暂停或取消后，执行说明统一显示在对话工具栏下方，服务端原因可以展开核对；没有新交互或后台活动时，固定进展区收起。正在发送、后台仍活跃或同步异常时保留反馈，不把暂停误当作任务完成，也不因此禁用普通聊天。

只在聊天里写“交给某某”不等于投递成功；实际消息、执行回执与成果分开记录。模型请求失败不等于完成，明确的服务商限流会标明 HTTP 429，不冒充余额不足或工作结束。

伙伴已交出子工作、正在等待有效回报时，不再仅因公开说明进展或保存阶段成果而自动唤醒原委托人。需要保留的进展变为知会；空等待不重复生成消息。判断依据是原委托下尚未交回子工作的最新状态，包含继续先前子工作的情况，不匹配发言关键词。排队和执行中的子工作可安静等待；以前已经停在等待态、这轮又没有新的接续安排时，仍保留上升路径，避免双方一直空等。成果、真实运行和未关闭责任仍可查看，后续结果照常交回；需要委托人回答或处理时，角色明确用send_message投递请求，不仅写在等待结束语中。失败或中断仍可唤醒委托人。这不取消独立复核，也不因等待而宣布完成。

## 聊天中的补充信息

支持原生工具调用的角色需要顾客补充信息时，可用 `request_questions` 把相关问题合成一张聊天内的问题卡。每题由模型指定单选或多选，可标记推荐选项；推荐不会自动选中。每题都能自己填写，也可以在选择后补充文字，或明确跳过。不需要跳到另一页，也不需要逐题发送。

选择和填写只改变草稿，整组提交后才作为一条顾客消息交回原提问角色继续处理。切换对话不会清空当前页面中的草稿；失败不自动重发，手动重试沿用同一请求标识。角色在委托中提问时，回答后承接原工作，不把补充信息当成另一份新任务。

可以继续直接聊天，不强制填表。新的自由聊天、目标变化或同角色发出新问题后，尚未回答的旧卡失效，避免用旧选项覆盖新方向；回答一位伙伴的问题不会使另一位伙伴的问题作废。目标已切换时，先前排队的旧表单回答不会再启动旧方案。跳过仅表示没有提供信息，不等于同意推荐、确认假设或授予操作权限。暂停或取消执行时不提交问题卡，仍可普通聊天。

旧的纯文本提问不会被事后猜测转换；结构化卡片来自角色实际调用工具，不是前端按问号识别。旧演示路径的单题澄清入口保持兼容。

## 文件与执行

- 成果发布后保存完整正文，可在成果板打开或下载。文件保存不代表代码已经正确运行。
- 伙伴用 `read_artifact` 按本群成果序号读取确切版本，默认仍返回完整正文。局部核对时可指定 `offset` / `length` 按 Unicode 字符读取（起点默认 0，每页默认 8000、最多 16000 字符），回执标明本页覆盖及后续起点。到末页不代表之前各页已经阅读，读取成功也不等于复核通过；SHA-256 与字节数始终对应原完整正文，不对应节选。分段不修改成果、下载包或复核版本，也不会自动裁剪模型已读取的工具历史。
- 需要读写项目、运行命令时，先在工作台绑定已配置的工作目录及权限。伙伴使用真实工具取得文件、命令输出和验证结果。
- 未绑定工作目录时仍能交流、发布文本成果，但不能把聊天中的代码或自述当作本机运行证据。
- 配置可选浏览器检查器后，原生伙伴可用 `browser_check` 实际操作本群最新已发布的静态网页副本，记录具体断言和文件版本，不需旧工作计划。失败、不可用、超时与历史范围分别保留；通过不等于复核或业务验收自动通过，见[浏览器检查](browser-checks.zh-CN.md)。
- 店长的交付结论会保留实际验证与未验证范围；它是模型判断，不是独立的宿主正确性认证。

成果板区分本轮最新发布、交付时锁定文件和历史版本，不把返工的每一稿平铺成多个当前成果。店长可以明确选择沿用旧文件，不需重新发布未改动依赖；默认不会把旧目标所有文件带入新交付。具体取回范围与版本绑定见[成果文件](artifacts.zh-CN.md)。

角色的上下文提供最近20条轻量回执引用，不重复附上整份命令输出。核查时可用 `read_receipts` 按 `role`（角色ID）、`message_seq`（原输入或委托序号）、`name`（工具名）组合筛选完整结果，或用索引中的真实 `run_id` 精确定位。角色名不是运行ID；传错会得到明确错误，不再静默返回空成功。更多历史可用 `before_seq` 向前翻页。

已知确切事件编号时可用 `receipt_seq` 定点读取同群原回执，其他筛选仍同时生效；不存在、跨群或无法关联到实际输入和运行的编号不会改读邻近记录。文件读取另有 `section: "file_reads"` 元数据分页，可按目录中复制的确切 `file_path` 查询。默认上下文最多列出8个路径的首次与最后一次历史读取，不复制源码；原文需按返回的 `read_args` 读取。首次被读到不等于原始基线，最后一次读取不等于当前磁盘，节选也不等于全文。重新绑定目录后不沿用旧绑定的来源索引；历史回执仍可作为只读材料查询，不能授权写入。

完整、未截断且编码明确的命令输出中，支持识别标准 unittest 结尾摘要。最近回执索引最多附带3份有来源编号的简短声明，并保留命令状态和退出码。这里的测试数量与结果是**程序输出的报告**，不是宿主认证的测试身份、覆盖率或复核批准；任意程序都能打印相同文字。输出不完整、有多份摘要或格式不明时不猜测汇总。需要说明改动原因、测试边界时，仍应比较实际历史源码、修改后文件和具体用例，不能从现行规则倒推原来的缺陷。

原生伙伴还会得到有界的工作指引目录，只在需要具体方法时使用 `read_skill` 阅读，或用 `list_skills` 翻页。内置指引覆盖问题溯源、实际检查、版本复核及交付讲解，宿主可额外登记项目 Markdown；读取不是执行、授权或验收，也不是每次开工的必经步骤。正文在可展开过程中按纯文本展示，配置失效不阻断普通工作。详见[按需工作指引](skills.zh-CN.md)。

从已有对话衍生的新群还提供冻结背景索引。角色可用 `read_background` 读取 `index` 引用列表、`goal` 来源目标、`source` 顾客原文或 `artifact` 文件正文；工程 ZIP 不填 `path` 时读原版本清单，填 `path` 后读成员。文本按 Unicode 码点分页，不读取来源群后来的消息或文件版本。该工具只在有继承背景的群里提供，暂停时也能用于只读讲解。历史材料不是当前任务要求、权限或通过验收的凭证，详见[衍生对话](conversations.zh-CN.md)。

明确关联到同一项目的普通群可按需使用 `read_project_history` 查历史交付、说明和冻结文件版本。默认只提供有界索引，不复制别群聊天；旧文件需在当前目标下重新核对，不自动落盘或加入新交付。未关联、私有及衍生群不加入实时目录，详见[同项目历史背景](project-history.zh-CN.md)。

回执只来自当前对话，正文范围以实际记录为准。命令长日志保留有界的开头和末尾，中间未保存；`read_receipts` 能补读完整回执对象，不能恢复被省略的日志。交付引用可逐字摘录任一已保存片段，但不能跨省略区或跨输出流拼接。历史测试通过不证明文件此后没有变化，也不证明所有场景正确；由复核者结合实际修改与风险决定复用哪些证据、补做哪些检查，而不是每一层机械地重跑或一概免检。

角色还会收到未结算操作的轻量索引，可用 `read_receipts` 的 `include_pending` 分页读取详情。纯本地的委托、消息、目标更新、问卷、复核与交付事件现在与对应回执原子提交；只有带该版本执行契约且原运行已结束的未结算操作，才能说明本地事件未提交。旧记录、文件发布与命令执行不能据此推断没有发生，仍须核对实际影响。索引不是重放授权，也不会自动重新领取原消息或恢复模型历史。

## 中途消息与暂停

执行者在模型调用之间交回调度，新顾客消息优先于下一份未开始的委托。已经发出的模型请求或命令不会因聊天瞬间终止；新的目标在后续操作边界生效，不承诺硬实时中断。

暂停后仍可询问状态和阅读成果，不会因此恢复文件写入或命令执行。伙伴间待处理消息保留在队列，恢复后再处理，不在暂停时消耗掉工作委托。暂停恢复需要明确操作。新契约下的进程中断可以通知店长核对后续作，内部通知默认折叠；它不重发旧请求、不绕过原委托和复核，也不把未知工具结果变成成功。具体范围见[暂停与故障恢复](recovery.zh-CN.md)。

## 兼容范围

支持工具调用的真实通道，网页普通新建、续聊及衍生对话默认使用消息协作，不依赖浏览器发送 `collaboration: "team"`。显式治理、旧结构化指派入口仍保留原语义；本地演示仍走原演示路径，不冒充自主执行。历史消息与成果不改写；闲置旧群在下一条普通消息时可切换，旧协作仍在途时不能同时切换引擎。原创建请求重试返回原会话，不借重试悄悄改换引擎。

第一版仍有上下文窗口与单轮执行资源边界，没有承诺任意长度任务永不出错。内阁投票不是默认关卡；持续共享会话、跨群协作、复杂任务资源调度还需要分别验证。
