# 事件查询与用量统计

事件库仍是唯一持久事实来源。查询优化没有新增用量缓存表，也不修改历史事件或审计签名。

## 当前查询边界

- `EventLog.read(task_id)` 保留原有列表接口，内部通过游标读取。
- `EventLog.iter_events(task_id=..., event_types=..., after_seq=...)` 按序号流式返回已登记的事件类型；空类型列表不查询。提前结束迭代的调用方应关闭生成器。
- 单任务快照只折叠该任务的事件；混合任务测试比较了它与全库折叠的结果。
- 已报告用量只读取 `msg.said` 和 `msg.challenge`，不反序列化成果正文。没有预算的驱动不扫描用量账本，伙伴状态也跳过不需要的预算读取。
- 自定义驱动给出的非法预算值会阻止调用，不能静默当成未设预算；伙伴页显示需要修正配置。
- 类型和任务索引在已有库重新打开时自动建立，事件内容、序号、链头与签名保持不变。

## 可重复基准

```powershell
python scripts/benchmark_event_queries.py
python scripts/benchmark_event_queries.py --artifacts 512
```

默认基准使用内存 SQLite，写入 128 项各 64 KiB 的成果和十条用量消息，比较全库读取与消息流式查询。两条路径必须得到相同用量。它不读取用户数据、不调用模型，也不安装依赖。

一次本机运行：全库路径的 Python 内存峰值约 8.2 MiB，筛选路径约 9.2 KiB，二者均得到 50 tokens。时间分别约 14.8 ms 和 0.5 ms。该结果只说明这一合成数据与本机环境，不是整个服务的性能保证；`tracemalloc` 不包含 SQLite 的全部原生内存。

完整审计核验、全任务列表与跨任务记忆仍有全库投影成本，需要分别评估。不能因为预算查询变快就宣称所有长历史路径都已优化。
