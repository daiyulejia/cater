# 第一轮真实模型验收

接入 API 后，可以测试店长规划、成员产出、独立复核和需求变更。这个测试不等于已经具备完整工程代理、权限沙箱或自动打包能力。

## 测试前

1. 使用 [单通道接入模板](../examples/README.md)，先让店长与成员共用一个已配置的 API 通道，不必同时购买多家服务。
2. 核对服务实际支持的完整接口地址和模型名。API Key 只放在本机环境变量里，不写进聊天、角色卡或 Git。
3. 在供应商侧设置可承受的消费限制。Cater 的已报告 token 预算不是账单金额、账户余额或严格费用上限，未知用量不会被当作免费。
4. 首轮只发送非敏感的小任务。模型服务将收到任务要求、角色信息、适用店规及相关成果正文；不要把私人工程或密钥作为测试材料。
5. 检查工作台是否显示真实接入状态。配置存在不等于连接成功，也不等于所有成员都能调用。

单通道示例使用 `--port 8766` 固定网页入口；端口已有服务时先确认正在使用哪套配置，不能只换浏览器地址就认为换了模型。更改服务进程的环境变量或配置后需要重启服务。重启前等待当前活动结束；不要用重启绕过结果不明的工作。

## 第一件小任务

在聊天里发送：

> 帮我整理一份中文的个人作品集页面需求。只交付一份可阅读的 Markdown，不写代码、不联网、不操作本地文件。包含目标用户、三个主要内容区，以及五条可检查的验收标准。不确定的内容请明确标出，不要虚构我的经历。

观察这些事实，而不只看回复是否流畅：

- 店长给出具体工作及验收安排，而不是把原话分别转发给每个成员。
- “要求与安排”里能追溯到顾客的要求；没有为了凑人数增加无关工作。
- 成员确实提交可打开的正文，不是只有“已完成”的一句话或不存在的链接。
- 独立复核能引用正文。证据不足应保留待验收，不应为了结束任务制造肯定结论。
- 阶段通过不被显示成整个项目已经验证完成。
- 店长最后按当前要求核对全部正文，依据齐全后才出现“已交付”和交付包；交付说明包含选择原因、复查方法与未覆盖范围。

这里先不运行本地代码检查。API 返回代码正文不等于已经安装依赖、执行文件或通过测试。

## 中途改变要求

在同一对话补充：

> 调整一下：作品集主要面向 Agent 开发岗位，突出工程经验，不要虚构 NLP 研究成果；旧的其他要求保留。

预期旧计划停止放行，新计划记录本次要求与受影响的工作。沿用旧正文时必须重新验收；旧检查记录只能保留在历史中，不能冒充新版本的检查结果。

再发送“进度怎么样？”和“继续”：前者应读取状态回复、不改目标；后者推进有效计划，不把已经通过的工作重新执行。混合句子如“继续，但删掉经历介绍”属于要求变化，不是单纯续做。

## 停止与失败

连接失败、额度不足、无效 JSON、缺少覆盖关系、循环依赖和规划期间要求变化，都应留下明确记录，不应伪造一次成功。

遇到“调用结果不明”，先核对供应商调用结果和日志；不要不停点击继续或重新发任务。Cater 目前没有完整的自动恢复确认界面。也不要把模型建议的检查命令直接交给主机执行，临时成果副本并不是操作系统沙箱。

## 如何记录

保留任务 ID、模型配置（不含密钥）、最终正文、需求变更前后计划、验收记录、已报告用量和失败原因。将“系统控制逻辑正确”与“模型实际产出合格”分别记录：离线测试通过只能证明前者的一部分，真实任务仍需要实际核对。
