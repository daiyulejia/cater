# 持续自驱迭代铁律

这份约定规定 Cater 如何持续改进自身。它既适用于维护者，也适用于未来由 Cater 驱动的自治复盘流程。

## 出发点

Cater 的目标不是制造会开不完的多 Agent 系统，而是帮助人类把目标交给一个可观察、可纠偏、能交付成果的自治组织。持续迭代必须始终回到发起人的动机、真实用户的操作感受和可验证的工程证据。

## 每轮必查

每次成组变更或定期复盘后，至少检查：

1. 发起人目标：当前实现是否仍帮助用户把目标交出去并拿回可信成果？目标是否因新信息而变化？
2. 产品与交互：首次入口、下一步操作、过程解释和成果入口是否清楚？
3. 协作质量：Agent 是否在交换、接力或校正工作，而不是平行复述或为了投票而争论？
4. 可验证性：事件、投影、失败和成果能否回放；关键改动是否有针对性测试？
5. 可靠性与边界：driver、工具、MCP 或第三方 CLI 是否经过真实协议、失败模式和成本检查？
6. 成本与比例：任务分发、内阁、最高决策和复盘是否真的比更轻路径更有价值？
7. 开源采用：零服务体验、中文文档、示例和错误信息是否降低了第一次运行的门槛？

## 行动规则

- 有明确证据的缺口：自行修正，补验证，按成组提交记录“改了什么、为什么、结果如何”。
- 只有假设而没有证据：先用测试、回放、用户路径或小实验验证，不凭名称和直觉堆机制。
- 涉及外部权限、真实业务目标冲突或多轮无法消除的阻塞：清楚说明需要人类决定的唯一问题。
- 本轮没有实质改进：保持安静，不能为了“持续迭代”制造重构、事件或文档噪声。

## 停止条件

单个任务可以完成，但项目不会因为某个功能已实现而自动宣告完善。一次复盘只有在没有发现高优先级的可证实问题、所有改动已验证、且下一步不需要人类输入时才可以暂时收束；下一次定期复盘仍会从本约定重新开始。
