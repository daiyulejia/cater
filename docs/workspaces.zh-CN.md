# 绑定工程工作目录

Cater 的 Anthropic Messages 与兼容 Chat Completions 通道支持原生客户端工具回合。绑定工作目录后，消息协作中的伙伴可以按实际需要读取、搜索、创建和修改文本文件，并运行明确配置的程序；权限取决于所绑定的配置，不因角色自称有权限而扩大。旧治理工作项使用各自原有的执行和复核入口。

## 配置与入口

在本机准备一个工作区配置文件。`root` 必须是已经存在的绝对目录；程序路径应使用本机的实际绝对路径。以下示例中的 Python 路径需要替换：

```json
{
  "workspaces": [
    {
      "id": "example",
      "title": "示例工程",
      "root": "C:/projects/example",
      "mode": "execute",
      "commands": {
        "python": ["C:/Python312/python.exe", "-B"]
      },
      "checks": [
        {
          "id": "tests",
          "title": "工程回归测试",
          "command": "python",
          "args": ["-m", "unittest", "discover", "-v"],
          "cwd": "."
        }
      ],
      "timeout": 60
    }
  ]
}
```

启动已有模型配置的工作台：

```bash
python -m cater --drivers drivers.json --roles roles.json --workspaces workspaces.json web --port 8766
```

在任务的“工作目录”入口选择预配置目录。保存绑定不会自动执行任务；继续当前任务时会重新核对计划。网页不能提交任意根目录或自行增加程序权限。相同目录内的工具工作通过协作锁串行执行。

新对话也可在首次发送前选择目录；创建、目录绑定与首次执行意图在同一事务保存。重试未知创建必须保留原目录和请求标识，不能将同一请求换绑到另一目录。衍生对话不自动继承父任务的目录授权。

命令行也可以查看和绑定：

```bash
python -m cater --workspaces workspaces.json workspace TASK_ID
python -m cater --workspaces workspaces.json workspace TASK_ID --bind example
python -m cater --drivers drivers.json --roles roles.json --workspaces workspaces.json new "修复工程中的问题" --workspace example --run
```

首次绑定不填写版本。以后更换或解除绑定，必须用查询结果中的 `revision` 作为 `--expected-revision`。工作区、命令或检查配置变化会使旧计划和验收失效，需要重新核对。

## 三种权限

| 模式 | 工具 |
| --- | --- |
| `read_only` | 目录列表、UTF-8 文本读取、字面文本搜索 |
| `edit` | 上述能力，加文本写入和按需创建子目录 |
| `execute` | 上述能力，加配置的程序别名与参数执行 |

已有文件的写入必须携带当前内容的 SHA-256；新文件使用 `expected_sha256=null`，不会覆盖已存在文件。发布使用临时文件、协作锁和写前复核，拒绝已观察到的版本变化。它不能与不遵守协作锁的任意外部写入者进行不可分割的比较并替换。

文件工具拒绝目录越界、已观察到的符号链接、junction/reparse point、硬链接、Git 元数据及常见凭据路径。搜索跳过依赖目录和二进制内容，并明确标记截断。每个文本文件最多 1 MiB，单次读取最多 65,536 字节。

**`execute` 是宿主执行权限，不是操作系统沙箱。** 程序别名限制可启动的程序，不限制解释器参数、脚本自身的文件或网络能力。命令使用清理后的环境，不默认继承 API Key；可显式放行不属于常见密钥名称的环境变量。只给可信工作内容配置需要的程序。进程组或 Windows Job 负责进程生命周期，不能替代文件或网络隔离。

工具会在分派工作区动作前核对声明中的字段、类型、取值和范围，不自动把字符串数字或布尔值转换为数字。此时拒绝返回 `invalid_arguments` 和 `not_started`，指出已声明的错误字段，不回显参数值；原生聊天与旧工作项均可据此修正请求，不把它当成未知命令副作用。实际执行后的错误及既有待核对操作不会因此解除。

## 实际成果与验收

消息协作中的角色可以直接使用 `workspace_read`、`workspace_write`、`workspace_run` 等已提供工具；已写好的文件可用 `publish_workspace_file` 读取真实正文后发布。未绑定目录时仍可发布文本成果，但不能因此声称已经运行命令或完成浏览器验证。下面的 `workspace_files`、独立验收门等说明针对旧治理工作项，不是普通聊天必须经过的流程。

单份内联文本成果最多 65,536 个 UTF-8 字节。源文件超限、不可读或文件名不适合实际落盘时会在发布前明确拒绝，不发布节选，也不将这次拒绝当作发布影响未知。修正路径、内容或拆分文件后可以继续；真正发布后发生的落盘异常仍需核对，不因此自动重复操作。

执行角色用最终回复中的 `workspace_files` 列出至多 6 个相对文本路径。宿主重新读取真实文件并计算摘要，每份交付正文最多 65,536 字节，总成果最多 8 份。当前单次源码捕获不支持同名文件，较大工程需要拆分或另行扩展工程归档能力。

工具开始、结果、模型用量和源码捕获分别记录事件。命令退出码为零只表示该命令成功，不自动使工作项通过验收。项目配置了 `checks` 时，Cater 将已提交的源码按捕获的相对路径放入临时目录重新检查，随后由独立复核者判断检查是否与要求相关。整体行为检查再次执行，使用独立回执。

整体验收可分别引用源码正文或当前版本的实际执行回执。若原文被误挂到一个现有源码编号下，只有它能唯一匹配当前实际回执时才修正来源编号，并保存修正记录；不改引文、通过/失败判断或未验证范围。项目本身包含 `manifest.json` 或 `handoff.md` 时，Cater 元数据移到独立目录，避免覆盖已验收源码。

临时副本仅包含已提交的源码及相应前置成果，不复制当前目录中未提交的文件、依赖或凭据。依赖安装、复杂多包构建、平台 SDK、长期预览服务及二进制交付仍需后续接入。交付包表示经过验收的版本，不表示宿主工作目录此后没有发生变化。

若工具已完成而最终交接回复格式无效，内置 API 通道允许一次无工具的回复整理；保留原回复诊断、真实工具回执与两次用量，不重新执行修改，也不因此改变验收结论。

## 中断与恢复

每条工具开始记录必须在执行前提交，外层未提交的数据库事务不能启动工程工具。每次模型、工具和项目检查前核对工作认领、任务要求、权限及暂停版本；暂停再恢复后，旧批次不能沿用授权。

执行轮次也冻结控制版本，暂停再恢复不会让旧轮次继续派下一个工作。后台执行者在调用边界重新检查配置文件，撤销、损坏或删除配置会停用旧权限；在途操作仍可能返回。持续有进展的工程执行会在认领到期前续期，已过期或版本变化的认领不能续期复活。

工具开始后缺少完整结果，或命令超时、进程清理/输出未完整结束时，保留待核对状态。普通“继续”不会重放这些操作。确认执行已停止并核查实际文件和进程影响后，操作员可以追加核对记录：

```bash
python -m cater --workspaces workspaces.json workspace TASK_ID --reconcile STARTED_SEQ --invocation-stopped --reason "实际核对的文件、进程及影响说明"
```

该命令是人工核对声明，目录锁释放本身不证明遗留进程已经停止，也不证明没有副作用。核对最后一条未知工具后释放对应工作认领；下一轮读取现有文件继续，不重放旧批次。已知服务商 429 拒绝与未知工具影响分别处理，不自动重复计费请求。

若工具回执完整，但模型或交接回复中断导致工作认领待核对，使用同样的核对条件，将 `--reconcile STARTED_SEQ` 换成 `--reconcile-work ATTEMPT_ID`。这只释放已核对的认领，不将任务标记为通过，也不自动再次调用模型。
