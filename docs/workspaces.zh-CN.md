# 绑定工程工作目录

Cater 的 Anthropic Messages 与兼容 Chat Completions 通道支持原生客户端工具回合。绑定工作目录后，消息协作中的伙伴可以按实际需要读取、搜索、创建和修改文本文件，并运行明确配置的程序；权限取决于所绑定的配置，不因角色自称有权限而扩大。旧治理工作项使用各自原有的执行和复核入口。

## 配置与入口

已交付成果仍可追问和核验。交付后新发送、直接给角色的顾客消息，可使用工作区原有的
`execute` 权限运行检查，无需为了核对一句说明重开目标；旧交付版本不会因此更新。
旧委托、内部通知和已结束的执行不能借此继续运行。暂停、权限变更及待核对操作仍会阻止执行。
这里不是只读沙箱：配置的程序仍可能修改本机文件或访问网络，命令权限与安全边界不变。
运行后是否改动工程应据实际文件核对，不能把“用于核验”当成无副作用的保证。

在本机准备一个工作区配置文件。`root` 必须是已经存在的绝对目录；程序路径应使用本机的实际绝对路径。以下示例中的 Python 路径需要替换：

```json
{
  "workspaces": [
    {
      "id": "example",
      "title": "示例工程",
      "root": "C:/projects/example",
      "mode": "execute",
      "commands": {
        "python": ["C:/Python312/python.exe", "-B"]
      },
      "checks": [
        {
          "id": "tests",
          "title": "工程回归测试",
          "command": "python",
          "args": ["-m", "unittest", "discover", "-v"],
          "cwd": "."
        }
      ],
      "timeout": 60
    }
  ]
}
```

启动已有模型配置的工作台：

```bash
python -m cater --drivers drivers.json --roles roles.json --workspaces workspaces.json web --port 8766
```

在任务的“工作目录”入口选择预配置目录。保存绑定不会自动执行任务；继续当前任务时会重新核对计划。网页不能提交任意根目录或自行增加程序权限。相同目录内的工具工作通过协作锁串行执行。

新对话也可在首次发送前选择目录；创建、目录绑定与首次执行意图在同一事务保存。重试未知创建必须保留原目录和请求标识，不能将同一请求换绑到另一目录。衍生对话不自动继承父任务的目录授权。

宿主可在配置顶层显式添加 `managed` 模板，例如 `{"workspaces":[],"managed":{"root":"F:/CaterWorkspaces","mode":"edit"}}`。基目录须预先存在，模式须明确指定；`execute` 模式的程序权限仅来自模板自己的 `commands`（别名到固定 argv 数组），另支持 `env_allowlist`、`timeout`，不复制既有工程权限。`managed` 缺省或为 `null` 时关闭。目录按数据库路径命名空间和任务 ID 分配并持久保留，不是操作系统沙箱。

**自动分配入口范围：**目前主新建入口 `POST /api/tasks`（调用 `task_requests.prepare`）及 CLI `new` 支持宿主启用后的默认分配；请求省略 `workspace_id` 才采用默认策略，显式 `null` 保持无目录，显式已有 ID 优先，`__managed__` 表示明确选择独立目录。CLI 对应省略选项、`--no-workspace`、`--workspace ID` 和 `--workspace __managed__`。旧表单 `/tasks` 仅经过 `prepare` 的分支适用；直接调用 `Runtime.create_task`、`POST /api/tasks/{id}/derive`、`rooms.start_task` 均不会自动分配，衍生任务也不继承来源工作区权限。因此不能将此能力理解为所有创建 API 都会自动绑定；这些旁路创建后仍须通过工作区绑定入口明确选择目录。

命令行也可以查看和绑定：

```bash
python -m cater --workspaces workspaces.json workspace TASK_ID
python -m cater --workspaces workspaces.json workspace TASK_ID --bind example
python -m cater --drivers drivers.json --roles roles.json --workspaces workspaces.json new "修复工程中的问题" --workspace example --run
```

首次绑定不填写版本。以后更换或解除绑定，必须用查询结果中的 `revision` 作为 `--expected-revision`。工作区、命令或检查配置变化会使旧计划和验收失效，需要重新核对。

## 三种权限

| 模式 | 工具 |
| --- | --- |
| `read_only` | 目录列表、UTF-8 文本读取、字面文本搜索 |
| `edit` | 上述能力，加文本写入和按需创建子目录 |
| `execute` | 上述能力，加配置的程序别名与参数执行 |

原生消息协作在这三种模式下均可把明确选择的可读文件发布为工程 ZIP（包括二进制）。它只读取绑定目录，不在该目录写文件或执行工程；快照写入 Cater 成果存储。

已有文件的写入必须携带当前内容的 SHA-256；新文件使用 `expected_sha256=null`，不会覆盖已存在文件。发布使用临时文件、协作锁和写前复核，拒绝已观察到的版本变化。它不能与不遵守协作锁的任意外部写入者进行不可分割的比较并替换。

`workspace_write` 支持整文件、单片段和同文件多片段三种写入方式：单独提供 `content` 时是整份新正文；提供 `old_text` 时，`content` 只是该片段的替换文字；提供 `edits` 时省略根级 `content` 和 `old_text`，一次提交多处修改。已有文件仍须使用最新读取的完整文件哈希。局部匹配冲突后，可以重读并选唯一片段，也可以在理解当前全文后选择整文件重写；宿主不会自动切换模式或覆盖新版本。

修改已有文件的一个片段时，`workspace_write` 可额外提供 `old_text`，此时 `content` 是替换内容，而不是整份文件。例如用读取结果中的 `sha256` 作为 `expected_sha256`，将唯一的 `"return 1"` 替换成 `"return 2"`。原文按字面精确匹配，必须非空且只出现一次，重叠匹配也视为歧义；不会忽略空白、换行或大小写，也不使用正则。替换内容可为空。哈希过期、无匹配或有歧义时不写入，应重新阅读并判断；该方式不能创建文件。未修改的字节保持原样，结果仍受 1 MiB 限制；回执记录替换次数及修改前后的文件哈希，不代替运行检查或独立复核。

同一文件的配套修改可以使用 `edits: [{"old_text": "原片段", "content": "新片段"}, ...]`，共 1–32 项。所有片段都在同一份原文上定位，不会匹配前一项刚生成的新文字；区间不能重叠，相邻区间可以一起修改。任一项失败时整批不写入，而不是留下半成品。原文与替换文字合计最多 1 MiB，最终文件也最多 1 MiB；仍只有一次原子发布和一个最终哈希，不能跨文件事务。审计只保存有界的片段长度与哈希，不重复保存片段正文。批量编辑是可选能力，不强制角色改用它，也不代表已证明真实模型能节省多少 token。

文件工具拒绝目录越界、已观察到的符号链接、junction/reparse point、硬链接、Git 元数据及常见凭据路径。搜索跳过依赖目录和二进制内容，并明确标记截断。每个文本文件最多 1 MiB，单次读取最多 65,536 字节。

**`execute` 是宿主执行权限，不是操作系统沙箱。** 程序别名限制可启动的程序，不限制解释器参数、脚本自身的文件或网络能力。命令使用清理后的环境，不默认继承 API Key；可显式放行不属于常见密钥名称的环境变量。只给可信工作内容配置需要的程序。进程组或 Windows Job 负责进程生命周期，不能替代文件或网络隔离。

新命令回执的 `execution_context` 仅记录外层启动配置：版本 `1`、`invocation=direct_argv`、`environment=minimal_with_allowlist`、`path_policy=os_default/allowlist_configured` 及平台 `win32/linux/darwin/other`。不保存环境变量值或软件清单；默认 PATH 使用 `os.defpath`，显式允许配置也不保证等于顾客终端。查找未命中不证明整机未安装，按 argv 启动不证明子程序没有 shell，配置记录不证明程序启动成功。交付引用可冻结这组来源事实；旧回执没有字段时保持未知，不追补推测。

Windows 精简环境还提供固定 `PATHEXT=.COM;.EXE;.BAT;.CMD`，使 PowerShell 能识别原生可执行程序，不默认继承用户的脚本/文件关联扩展。宿主显式在 `env_allowlist` 允许该变量后，可用宿主值覆盖，包括空值；Windows 允许项按大写环境键写入，避免大小写变体产生重复项。POSIX 保持大小写敏感，也不注入此 Windows 默认值。这不新增程序别名或命令权限，子程序仍需可信，未知影响与进程收尾仍按原机制核对。

工具会在分派工作区动作前核对声明中的字段、类型、取值和范围，不自动把字符串数字或布尔值转换为数字。此时拒绝返回 `invalid_arguments` 和 `not_started`，指出已声明的错误字段，不回显参数值；原生聊天与旧工作项均可据此修正请求，不把它当成未知命令副作用。实际执行后的错误及既有待核对操作不会因此解除。

命令启动前还会检查 `cwd`。目录不存在或无法访问时返回 `cwd_unavailable`、`complete=true` 和 `not_started`；越界、受保护路径、链接或非目录仍保留对应的安全拒绝。此时没有启动程序，可核对实际目录后修正 `cwd`，不会仅因这个输入错误锁住后续命令。对发布成果副本运行时，`cwd` 相对于解包副本的实际目录，不是 ZIP 文件名。该说明不把启动后的错误改成“未执行”，也不清除旧回执中已存在的未知操作。

启动进程后若没有拿到可信结果，例如回执缺失、无法读取、JSON 损坏或字段异常，会保留 `effects_unknown`，继续要求核对实际影响，不把它当作可直接重试的普通启动失败。已采集的 stdout/stderr 仍照实保留；输出完整也不代表退出状态或副作用已确认。

子进程报告的 `launch_error` 也不单独证明命令从未执行；只要没有可信退出状态，仍以 `process_failed` 保留待核对操作，不能仅凭错误名称重跑。

命令回执中的 stdout/stderr 摘录各不超过 8 KiB。短输出照常返回；长输出分别保留开头 `excerpt` 和末尾 `tail_excerpt`（`preview_mode=head_tail`），不能拼成连续全文。中间内容未保存，展开回执也无法恢复；先读已保存的失败末尾，不因截断就自动重跑命令。`bytes`、`sha256` 对应实际采集的完整原始流，`complete` 表示采集是否结束，与预览是否截断分开；无效 UTF-8 的显示会使用替换字符，不是二进制日志副本。

每条输出流的 `utf8_valid` 表示已采集字节的 UTF-8 有效性：`false` 表示发现无效字节，`true` 表示采集结束且全部有效，`null` 表示采集未结束且尚未发现无效字节；历史回执缺少此字段时也视为未知。检测包含未保留的中间输出，但不猜测原始编码，不改变命令退出状态。有效的完整流仍可能因预览截断而显示不完整字符，不能用此字段证明预览完整。遇到乱码先说明证据限制；后续检查可显式指定已确认的编码或使用 ASCII 安全诊断，不为修复显示而盲目重跑有副作用的命令。

交付引用会保留来源回执中已记录的各输出流编码状态，下载的交付说明也会提示无效或未知状态。这是整条流的诊断，不证明当前引文本身损坏，也不表示命令失败；旧交付不会因此补造诊断。

## 实际成果与验收

`workspace_run` 的 `command` 是宿主预配置的别名，`args` 是追加到该程序前缀后的独立参数，不是替换程序，也不是一整段 shell 命令。例如上面的 `python` 配置配合 `args=["-m", "unittest", "discover", "-v"]`，才会运行测试发现；如果别名 `check` 指向固定检查脚本，追加一个文件名不会自动改成运行那个文件，是否接受参数由脚本决定。

配置检查入口时，应让它能执行工程中新增加的测试，并对不支持的参数明确报错，不要静默忽略。角色需核对回执中的实际 `argv`、测试名称或数量及失败信息：退出码零、`outcome=passed` 只说明程序成功退出，不证明预期测试被执行，更不等于整个任务已经验收。缺少所需入口时，应说明哪些检查未执行；不能把文件已写好、参数已传入或命令名叫 `check` 当成执行证据。

`workspace_run` 还支持可选的 `stdin`，将至多 65,536 个 UTF-8 字节作为标准输入传给已配置的程序，不自动追加换行或 BOM；空字符串表示发送空输入并结束，省略时仍关闭标准输入。它适合程序支持的文本输入或临时检查代码，不需要先在工程创建辅助脚本。例如上述 Python 配置可用 `{"command":"python","args":["-"],"stdin":"print('stdin example')\n"}` 从标准输入执行这段代码；这只是输入方式示例，不是工程检查或覆盖证明。

程序必须支持这种方式，角色应核对实际别名前缀和参数；宿主不会自动选择解释器、添加 `-`、移除隔离参数或修改导入路径。特别是 Python 配置了 `-I` 时，不会自动从当前目录导入工程模块，需要依据真实环境明确处理。程序可以忽略标准输入；回执的 `stdin` 只记录配置内容的编码、字节数和 SHA-256，不证明程序读过或执行过它。实际结果仍以 stdout/stderr、退出码和所需观察为依据。非零退出前已取得的局部观察可以保留，目标观察之前就失败的检查不能说成已取得那个结果。

标准输入不是密钥通道：请求参数仍保存在工具开始记录，也会作为任务资料发给模型服务。输入没有扩展程序权限，但配置的解释器仍可能写文件、访问网络或启动其他程序；这不是只读或 OS 沙箱，也不自动保证工程不变。超时、进程清理和未知副作用沿用原机制，不因使用临时输入而自动重试。

原生消息协作中的 `workspace_run` 可额外传入 `artifact_seqs`，直接在本群当前已发布版本的临时副本中运行同一受信任命令。例如 `{"command":"python","args":["-m","unittest","discover","-v"],"cwd":"package","artifact_seqs":[123]}` 检查工程 ZIP #123 内的 `package` 目录；ZIP 不含父目录时用 `cwd="."`。宿主从已发布字节校验、还原目录和文件，不必由角色另写解压、日志解码脚本。最多 128 个文件、单文件 16 MiB、总计 32 MiB，必须列全所需文本成果或完整 ZIP；不复制工作目录内未发布的依赖、输入、环境文件，不接受其他群或同名过期版本。

该方式仍需绑定目录的 `execute` 权限及现有程序别名，并持有原目录的协作锁。`cwd` 此时相对成果副本；别名固定前缀内的相对脚本路径也将从此目录解析，宿主检查器应使用适合该布局的配置。临时副本不是 OS 沙箱，程序仍具有宿主权限，超时或未知影响沿用现有待核对机制。回执保留实际命令、输出、`checked_artifacts`（成果序号及摘要）、`checked_files`；`artifacts_unchanged` 只检查原输入文件是否保留，不表示没有生成新文件。`scope_current` 表示目标、权限和发布版本仍适用，`artifact_check_valid` 是二者同时成立；即便为真，也须结合退出码、测试输出和覆盖范围判断，不自动产生批准。副本原输入被改写或检查中出现新目标、新版本时，不应将其当成当前原成果的有效核验。

工程清单中的 `executable` 标记会保留在 `checked_files`；POSIX 上还原并核对执行位。Windows 不提供相同的权限位语义，回执的 `executable_flags_checked` 为 `false`，不能据此声明已验证 POSIX 直接执行行为。

需要用同一批输入比较确切旧新版时，可改用 `artifact_versions`，与 `artifact_seqs` 互斥。例如 `{"command":"python","args":["-"],"stdin":"...比较代码...","cwd":".","artifact_versions":[{"artifact_seq":123,"directory":"before"},{"artifact_seq":124,"directory":"after"}]}` 会将两个版本分别放入独立目录。若 ZIP 原成员是 `package/main.py`，实际副本路径就是 `before/package/main.py` 与 `after/package/main.py`。文本成果也保留原文件名；不必手抄旧源码、改成果名或猜临时绝对路径。

这个显式模式允许本群同名历史版本，不放松原 `artifact_seqs` 或浏览器检查的最新版本要求。每个序号只选一次；目录必须是独立的单层便携名称，拒绝受保护名称、路径越界及大小写或 Unicode 等价冲突。所有版本合计仍限 128 文件、单文件 16 MiB、总 32 MiB，先核对总预算、清单和路径再读取 ZIP 字节。无效选择会在启动前拒绝，不回退实际工程目录；不会继承旧版本的批准或执行权限。

可确定的版本参数错误保留 `invalid_artifact_check`、`complete=true` 和 `outcome=not_started`，另给固定 `reason`、`fields` 与修正说明，例如两个版本共用或等价的目录返回 `version_directories_conflict`。检查当前多个已发布文件时，可用 `artifact_seqs` 放入同一副本；比较不同版本时，`artifact_versions` 的每项需要独立目录。宿主不自动改参或合并目录，未知异常仍使用脱敏提示；拒绝信息不证明其他输入都正确，也不清除既有待核对操作。

回执中 `artifact_selection=version_directories`，`checked_artifacts` 记录所选序号、摘要、目录和检查末观察到的最新发布序号；`checked_files.source_path` 是原路径，`path` 是实际挂载路径。`scope_current` 在此模式表示目标、控制、目录授权及所选确切源字节仍有效，**不表示最新版**。`selected_versions_current` 单独表示所有所选版本是否都是最新发布；`null` 表示无法确定，不能按“是”处理。明确选择的旧版可以留下有效的历史运行证据，即使检查时又有同名新发布，也不会因此变成新版验收。`artifact_check_valid` 仍仅表示范围有效且原输入副本未改，不证明兼容、覆盖充分或独立复核通过；退出结果、检查内容和最终批准版本要分别核对。

网页沿用已有“工具过程”入口，在对应命令下展开“版本副本检查详情”，可分别查看执行结果、版本新旧及原路径到挂载路径的映射。详情默认折叠，不在主聊天重复铺开文件清单或输出日志。

消息协作中的角色可以直接使用 `workspace_read`、`workspace_write`、`workspace_run` 等已提供工具；已写好的文件可用 `publish_workspace_file` 读取真实正文后发布。未绑定目录时仍可发布文本成果，但不能因此声称已经运行命令或完成浏览器验证。下面的 `workspace_files`、独立验收门等说明针对旧治理工作项，不是普通聊天必须经过的流程。

单份内联文本成果最多 65,536 个 UTF-8 字节。源文件超限、不可读或文件名不适合实际落盘时会在发布前明确拒绝，不发布节选，也不将这次拒绝当作发布影响未知。修正路径、内容或拆分文件后可以继续；真正发布后发生的落盘异常仍需核对，不因此自动重复操作。

原生消息协作可使用 `publish_workspace_archive` 发布完整工程快照。例如 `{"filename":"project.zip","summary":"已运行本机测试，具体范围见回执","paths":["src/main.py","tests/main.py","src/__init__.py","assets/logo.png"]}`。`paths` 明确选择实际文件，不自动递归目录；相同文件名可以位于不同子目录，保留空文件、二进制字节及源文件的可执行标记。最多 256 个文件，单文件 32 MiB，总输入 64 MiB，ZIP 不超过 65 MiB。受保护路径、链接、特殊文件、便携命名冲突或观察到的并行变更会使整个快照拒绝，不交付部分工程。

ZIP 字节保存在事件数据库的独立内容表，事件只保留文件清单、字节数和 SHA-256；备份应使用 SQLite 备份方式保留完整数据库，而非仅导出事件 JSON。复核绑定工程 ZIP 的确切序号与哈希，修复后重新发布、交回原复核者。`read_artifact` 默认读取工程文件清单，附 `path` 后按 Unicode 字符分页读取其中 UTF-8 文本；二进制仅返回字节数与哈希，不表示已经检查图片或运行程序。顾客可在原成果区展开文件清单并下载该版本 ZIP；最终交付包包含冻结的原 ZIP，不从后来变化的工作目录重新打包。发布快照不等于验收通过，仍须记录真实检查与复核范围。

旧治理工作项的执行角色用最终回复中的 `workspace_files` 列出至多 6 个相对文本路径。宿主重新读取真实文件并计算摘要，每份交付正文最多 65,536 字节，总成果最多 8 份。该旧源码捕获仍不支持同名文件；原生消息协作的多目录工程使用上述工程归档能力。

工具开始、结果、模型用量和源码捕获分别记录事件。命令退出码为零只表示该命令成功，不自动使工作项通过验收。项目配置了 `checks` 时，Cater 将已提交的源码按捕获的相对路径放入临时目录重新检查，随后由独立复核者判断检查是否与要求相关。整体行为检查再次执行，使用独立回执。

整体验收可分别引用源码正文或当前版本的实际执行回执。若原文被误挂到一个现有源码编号下，只有它能唯一匹配当前实际回执时才修正来源编号，并保存修正记录；不改引文、通过/失败判断或未验证范围。项目本身包含 `manifest.json` 或 `handoff.md` 时，Cater 元数据移到独立目录，避免覆盖已验收源码。

旧治理工作项的临时副本仅包含已提交的源码及相应前置成果，不复制当前目录中未提交的文件、依赖或凭据。依赖安装、复杂多包构建、平台 SDK、长期预览服务仍需按实际任务配置与完善；工程 ZIP 可保存已有二进制产物，但不自动提供平台构建环境。原生消息协作的[浏览器检查](browser-checks.zh-CN.md)可检查工程 ZIP 中明确选择的静态页面及本地依赖，保留目录和二进制字节，但不启动任意后端或执行安装脚本。交付包表示记录的验收版本，不表示宿主工作目录此后没有发生变化。

若工具已完成而最终交接回复格式无效，内置 API 通道允许一次无工具的回复整理；保留原回复诊断、真实工具回执与两次用量，不重新执行修改，也不因此改变验收结论。

## 中断与恢复

每条工具开始记录必须在执行前提交，外层未提交的数据库事务不能启动工程工具。每次模型、工具和项目检查前核对工作认领、任务要求、权限及暂停版本；暂停再恢复后，旧批次不能沿用授权。

执行轮次也冻结控制版本，暂停再恢复不会让旧轮次继续派下一个工作。后台执行者在调用边界重新检查配置文件，撤销、损坏或删除配置会停用旧权限；在途操作仍可能返回。持续有进展的工程执行会在认领到期前续期，已过期或版本变化的认领不能续期复活。

内建的文件读取、列表和搜索没有写入职责。它们丢失回执时，原调用仍保留为未返回记录，但不会单独锁住后续写入、工程快照或交付；新工作需要时重新读取现状，不补造旧读取结果。活执行者的目录锁及权限、版本检查仍生效。这个例外不适用于运行命令、写入、恢复文件、未知工具或仅自称“只读”的外部工具。

工具开始后缺少完整结果，或命令超时、进程清理/输出未完整结束时，保留待核对状态。普通“继续”不会重放这些操作。确认执行已停止并核查实际文件和进程影响后，操作员可以追加核对记录：

```bash
python -m cater --workspaces workspaces.json workspace TASK_ID --reconcile STARTED_SEQ --invocation-stopped --reason "实际核对的文件、进程及影响说明"
```

该命令是人工核对声明，目录锁释放本身不证明遗留进程已经停止，也不证明没有副作用。核对最后一条未知工具后释放对应工作认领；下一轮读取现有文件继续，不重放旧批次。已知服务商 429 拒绝与未知工具影响分别处理，不自动重复计费请求。

若工具回执完整，但模型或交接回复中断导致工作认领待核对，使用同样的核对条件，将 `--reconcile STARTED_SEQ` 换成 `--reconcile-work ATTEMPT_ID`。这只释放已核对的认领，不将任务标记为通过，也不自动再次调用模型。
