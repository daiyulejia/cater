# 自动浏览器检查

可选检查器复用 Playwright，在独立浏览器上下文中检查静态 HTML 和浏览器内交互。支持原生消息协作的已发布文件，也保留旧工作项及其已验收直接依赖的检查。Python 核心仍然不需要第三方依赖。

## 安装与启用

需要 Node.js，先在仓库根目录执行：

```bash
npm --prefix tools/browser-check ci
node tools/browser-check/node_modules/playwright/cli.js install chromium
```

创建本地配置文件，例如 `.cater/browser-checker.json`，使用本机的绝对路径：

```json
{
  "command": ["C:/Program Files/nodejs/node.exe", "C:/work/cater/tools/browser-check/runner.mjs"],
  "timeout": 90
}
```

启动时显式启用：

```bash
python -m cater --drivers .cater/drivers.json --browser-checker .cater/browser-checker.json web --port 8766
```

`command` 是受信任的本机配置，不来自聊天或模型输出。运行时不会自动安装包、下载浏览器或切换其他工具。原生协作需要支持 `tool_turn` 的模型通道；旧流程的自动检查方案规划需要内置纯文本 API driver，演示和自定义执行型 driver 不会自动进入旧方案调用。

## 原生对话中的检查

启用检查器后，伙伴可以按任务需要调用 `browser_check`：提供本群最新已发布的 HTML、JS、CSS 等文件事件序号，以及入口、具体操作和断言。未配置时不会向模型提供这项工具；不需要为调用它另建旧工作计划或经过所有角色。

宿主读取这些固定版本的完整正文并校验哈希，在一次性目录准备副本；不把工作目录、任意 URL 或聊天中的文件路径交给浏览器。命令、超时、文件清单和环境由宿主决定，API 密钥、Node 注入参数和调试连接开关不会传给原生检查子进程。暂停或取消时不提供这个执行工具，在途检查可能返回，仍会保留记录。

至少包含一个可失败的 `assert_*`。`status: ok` 仅表示取得回执，实际结论看 `outcome`、失败步骤、退出码和被检查的文件版本；断言失败、工具不可用与超时分别记录。期间目标、控制或文件变化时标记 `scope_current: false`，只能作为历史记录。检查通过也不自动批准复核、结束任务或证明覆盖完整；伙伴应分析失败原因、修正并发布新版，再按需重检及交回复核。

检查中断且没有可信的进程结束回执时，不重复启动另一份检查，也不将未知调用作为最终完成。当前执行契约下，超时后若宿主已确认进程树清理及输出关闭，会保留超时失败但不永久占用待核对状态；后续可按需另发检查，不自动重放旧计划。真正未知的调用需可信本地操作者确认原进程停止并记录核对，接口见[故障恢复](recovery.zh-CN.md)。

具体步骤和实际值在现有折叠工具过程及审计回放中中文展示，截图仅保留元数据，不链接已清理的临时文件。店长的交付说明可引用匹配当前交付文件集的真实观测，不能把计划标签或预期值当作执行证据。该路径检查静态副本，不证明当前本地工程文件未变化，也不支持后端服务、安装包或访问外网。

`assert_js` 可附加 `observe` 表达式，在断言失败后采集当时需要核对的状态值。例如 `expression` 比较计数是否为1，`observe` 返回 `() => ({count: document.querySelector('#count').textContent})`，失败回执即可同时展示实际计数。通过时不执行采集；采集错、返回“通过”或改变页面，都不会改写原断言失败或继续后续步骤。表达式仍只在隔离页面执行，宿主不证明它是纯函数或测试逻辑正确。诊断最多等待1秒、保留1200 Unicode字符，报告总容量可能进一步节选；不是完整状态快照，也不代替复核。未提供时沿用原计划和回执行为。

## 旧工作项的执行与验收

有 HTML 成果且工作项需要实际检查时，独立检查者才会收到 [浏览器检查指引](../cater/packs/browser_check.md) 和有限的动作接口。模型可以选择具体操作、断言，或报告能力不足，不会加载全部工具目录。

检查器使用提交内容的临时副本，保存实际操作回执，并绑定工作项、验收条目、要求版本和成果摘要。测试报告可以检查其已验收直接依赖中的网页；依赖内容也必须与该报告提交时的版本一致。文件重名不会被静默覆盖。

命令成功不等于验收通过。复核者还需要检查断言是否覆盖要求、是否只是自我证明、是否错误地把测试初态设置当成功能验证。模型不能用自己的通过声明覆盖失败回执。

源码引用与运行证据分开校验。浏览器实际输出可以直接引用当前回执中的原文，不必假装错误信息写在源码里；成功断言的布尔结果也提供宿主生成的结构化观测文本，避免“检查通过却没有可引用证据”。计划中的步骤名称和预期值不能冒充实际观察，引用正确仍不能覆盖失败或不完整回执。

工具不可用、方案不支持、调用结果不明与实际断言失败分别保留；前几种情况不能当作代码缺陷。文本方案格式无效时允许一次带具体错误的纠正，此时还没有执行工具。若规划已明确结束且从未执行工具，后续新的明确继续请求可重新规划一次，同一请求不重复调用；执行中的规划或已有实际检查不会借此重放。工具恢复后可以通过现有显式 `verify` 入口补充新回执；当前尚无自动修复已执行测试或工具安装流程。

单份计划最多128步，实际执行仍有总时限。SVG/canvas 棋盘可用 `click_at` 在元素内指定 CSS 像素坐标进行真实点击，不必使用脚本重建游戏。JavaScript 表达式在打开浏览器前只做语法解析，语法错误归为检查方案不可用，不当作网页失败。语法正确仍不代表测试逻辑正确：必须核对前提、操作顺序和断言，不应为了消除红灯修改正确程序或削弱标准。

## 边界

- 当前只支持静态 HTML 及浏览器内 JavaScript，不支持后端启动、依赖安装、Android/iOS/桌面原生测试。
- 页面只能请求提交副本中的文件；外部网络、WebSocket、下载和已有登录态不可用。依赖 CDN 的页面需要先提供本地文件。
- 模型表达式只在浏览器页面内运行，不能作为 Node.js 或 shell 执行。表达式本身仍可能是无效测试，必须独立复核。
- 使用 Chromium 沙箱和独立上下文，但不宣称提供通用宿主机权限沙箱。只启用可信的执行器配置，保持浏览器更新。
- 支持工作项检查，以及符合静态网页能力范围的整体交付检查。整体检查使用与交付 ZIP 相同的 `work-N/文件名` 布局，独立记录 `integration_behavior` 回执，不沿用阶段检查冒充整体验收。混合后端或不支持的工程仍需显式 `verify`。

实际操作与失败原因可在过程记录中核对。截图摘要用于定位这次执行，不等于对布局美观或游戏规则正确性的证明。
