# 官方客户端接入（试验性）

Cater 可通过 Qoder CLI CN 的公开 ACP 接口使用外部 Agent，同时沿用
Cater 的文件、命令、派活、复核与交付工具。这不是桌面聊天窗口转发，
也不读取或导出客户端登录令牌。当前适配器为 `qoder_acp`，不是通用客户端兼容承诺。

## 准备与配置

先按 [Qoder 官方 ACP 文档](https://docs.qoder.cn/cli/acp) 安装、登录官方 CLI，
确认账号可用的模型与实际活动规则。桌面客户端已登录不代表 CLI 已登录；
ACP 使用 CLI 的认证状态。Cater 不负责注册、登录或购买套餐。

Windows PowerShell 中，带引号的可执行文件路径前需要 `&`：

```powershell
& 'C:/Tools/Qoder/qoderclicn.exe' login
```

路径只是示例，替换为自己的可信官方程序位置。个人配置保存在本地忽略目录，
例如 `.cater/config/`，不要提交账号信息、登录日志或真实模型配置。

在本地 `drivers.json` 中添加：

```json
{
  "drivers": [{
    "name": "official_client",
    "kind": "qoder_acp",
    "executable": "C:/Tools/Qoder/qoderclicn.exe",
    "model": "替换为账号实际可用的模型名称",
    "timeout": 180
  }]
}
```

复制已有角色配置到本地，保留组织与角色字段，把需要使用此通道的角色
`driver` 改为 `official_client`，也为 `organization.leader` 设置此字段。
若保留其他通道，必须同时提供那些通道的配置。多个角色可以共用通道，
但每轮执行有独立客户端会话，不共享活跃 session。

先用独立数据库和无敏感资料的测试工程：

```powershell
python -m cater --db .cater/client-trial.db --drivers .cater/config/drivers.json --roles .cater/config/roles.json --workspaces .cater/config/workspaces.json web --port 8766
```

配置工作目录见 [工程工作目录](workspaces.zh-CN.md)。端口被占用时选择其他端口；
不要覆盖正在运行的配置或用重启绕过未确认的操作。此通道用于聊天协作，
不提供旧式纯文本 `complete` 接口，不能替代所有历史规划/批处理入口。

## 执行与费用边界

- 实际模型名在握手时核对，不匹配则不发送任务；不自动回退到另一模型或付费通道。
- 客户端在临时启动目录运行，关闭内置工具与隐式 MCP 配置，工具由 Cater 提供。
  授权工作目录不作为客户端启动目录，避免加载工程内的客户端配置。
- 任务要求、角色上下文及工具结果会发给模型服务；只试用可外发的资料。
- 模型文本结束不等于完成委托。实际交还、复核与交付仍由工具回执和成果版本确认。
- 等待伙伴或正式交还后撤销本轮工具入口；取消、关闭不撤销已经发生的操作。
- 进程树管理与受管工具不是 OS 沙箱。CLI 本身是可信本机程序，依然具有宿主用户权限；
  本接入不承诺隔离恶意客户端、任意命令或远端服务。
- 当前外部模型 token 用量标记为未知。`token_budget` 不能据此提供严格费用上限；
  应在供应商侧核对活动、余额和消费控制，不把未知用量当免费或永久不限量。
- 当前受管启动参数固定单次模型输出上限为 2048 token，关闭客户端模型请求重试；
  `timeout` 可配置但不是总任务时限。大文件生成与长任务尚需专门验收，
  不能由小工程试验推定已能稳定完成。

## 异常核对

运行诊断区分本地等待超时、客户端退出、请求被拒绝、协议异常和连接不可用。
这些分类不等于完整根因：请求被拒绝不能直接认定余额不足；本地超时也不证明
远端停止执行或计费。记录不保存服务端异常原文，不自动重发可能已执行的请求。
旧记录没有分类时仍需核对，不能反推为超时。当前 `timeout` 是单次 ACP 请求的
等待期限，期间收到进展不会重置它；不是整个任务时限，也不是空闲超时。

新调用的事件记录还包含宿主观测：握手完成、尝试发送、首次公开进展、首次工具调用、
响应返回及收尾的相对毫秒时间，以及工具调用次数、公开进展次数和宿主工具耗时。
同时记录最后一次公开进展和最后一次工具结束的时间，便于核对等待发生在哪一段。
未出现的节点不填写；这些数值不是模型内部思考时间，也不证明远端是否执行或计费。
公开进展通知不等于工具已执行，工具调用次数不等于执行成功，仍以工具回执核对。
观测不保存私密思考或通知正文；旧记录没有这些指标时不能补猜。

正常关闭已确认的调用失败不会单独造成永久目录锁；工具自身的未知副作用仍须核对。
异常退出、无法确认客户端停止时，先查看记录：

```powershell
python -m cater --db .cater/client-trial.db external-run TASK_ID
```

确认对应进程及子进程已停止、实际文件与工具回执已检查，并且宿主运行已结束后，
才可使用返回的 `started_seq` 和 `started_hash` 登记核对结果：

```powershell
python -m cater --db .cater/client-trial.db external-run TASK_ID --reconcile 123 --expected-hash STARTED_HASH --invocation-stopped --reason "填写实际进程、文件与回执核对依据"
```

这是操作者的明确确认，不是自动检测进程已停止，不会取消活跃工作或自动重放请求。
这里“宿主运行已结束”要求数据库已有对应的 `team.run_finished` 记录。
如果主程序崩溃前未写入该记录，在实际确认原执行及子进程均停止后，
可在完整核对命令上额外添加 `--retire-host-run`。它只把该外部调用对应的
遗留宿主运行登记为中断，并原子保存核对结果；不收尾其他运行、不通知角色、
不调用模型。不要用再次运行任务来代替此核对。

活动运行仍持有任务时会拒绝核对。独立工具的未知副作用不能通过此命令一起清除；
需要按 [故障恢复](recovery.zh-CN.md) 与对应工具说明逐项核对，再发送新的监督输入继续。

## 验证范围

已在隔离的 Windows 工程中验证普通账本修复：真实角色派活、实际文件落盘、
命令回归、独立复核、正式交还和店长交付。离线回归覆盖两轮返工、暂停、
握手期间目标变化、无正式交还的文本结束以及未知调用恢复。
这不代表复杂工程、全部操作系统、长期运行或所有客户端版本均已验证。
Kimi、智谱等客户端尚未接入，需逐家核实官方接口、活动许可和能力后再扩展。
