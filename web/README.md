# Cater 对话工作台

这是 Cater 可选的 React 对话工作台。Python 运行时继续保持零第三方运行依赖；需要使用聊天式任务空间时，再启用本目录的前端依赖。

## 本地运行

只有从源码修改工作台时才需要构建。发布包会自带最近一次已验证的静态工作台。

构建并同步到 Python 包：

```powershell
.\scripts\build_web.ps1
```

首次执行前请先在 `web/` 目录运行一次 `pnpm install`。

仅验证前端生产构建时运行 `pnpm --dir web build`，产物位于 `web/dist/`，不会同步到 `cater/static`。构建使用 Vite 8 的 `build.rolldownOptions.output.codeSplitting`，将 React 运行时、共享第三方依赖与业务入口分块，保留默认 500 kB 告警阈值。任务图及图谱依赖首次打开时才加载；共享依赖仍在首屏加载，分块本身不等于减少其总下载量。性能测试直接构建内存产物，检查每个 JS 块不超过 500 kB、业务入口不超过 150 kB、静态依赖完整且无循环，以及聊天入口没有静态导入图谱依赖。

前端开发推荐 Node.js 24 与 pnpm 11。交互测试使用 Vitest 和 React Testing Library，仅属于前端开发依赖；Python 运行时依然零第三方依赖。

```powershell
pnpm --dir web test
pnpm --dir web lint
```

测试会模拟延迟响应，检查任务切换、草稿归属、重复发送、后台刷新和阅读历史时的新消息提示。GitHub 自动检查也会运行这些测试和前端构建。

真实浏览器布局回归单独启用，复用仓库已固定版本的可选工具，不要求普通前端测试隐式安装浏览器。先在 `tools/browser-check/` 执行 `npm ci --ignore-scripts --no-audit --no-fund` 和 `npm run install:browser`，然后在 PowerShell 中执行：

```powershell
$env:CATER_WEB_BROWSER_TESTS = '1'
pnpm --dir web exec vitest run --maxWorkers=2
```

未启用时仅跳过该浏览器布局用例，其余交互与构建预算检查照常执行。CI 会安装固定浏览器工具及 Linux 运行依赖并显式启用，覆盖手机与桌面的真实布局；无需模型 API 或生产数据库。

手动检查慢加载状态时，可在仓库根目录运行 `python tests/fixtures/workroom_latency.py`，访问 `http://127.0.0.1:8774/`。这个专用验证服务使用独立的 `.cater/qa/workroom.db`，故意延迟响应，结束检查后关闭即可。

然后回到仓库根目录，正常启动 Cater：

```powershell
python -m cater.cli web --port 8766
```

访问 `http://127.0.0.1:8766`。Cater 会从同一个本地地址提供工作台、API 和完整审计回放。

远程绑定时，Cater 会要求访问令牌和外部 TLS 边界。先设置 `CATER_WEB_ACCESS_TOKEN`，再用
`--host 0.0.0.0 --allow-remote` 启动；浏览器首次访问可使用
`https://你的地址/#access_token=你的令牌`。前端会立即移除地址栏里的片段，并只在当前浏览器会话向同源 API
发送令牌。不要分享含令牌的链接；Cater 不提供 TLS，请将远程服务置于 HTTPS 反向代理、VPN 或等效受控网络边界之后。

开发前端时，可以分别运行 `python -m cater.cli web --port 8766` 与 `pnpm dev`，再访问 `http://127.0.0.1:5173`。Vite 会把开发请求代理给 Cater 的 API。

## 产品边界

普通聊天、新建与衍生任务请求带 `collaboration: 'team'`；演示后端可以回退到原流程。前端读取详情根级 `team`（兼容 `task.team`），仅在 `enabled` 时显示团队进度，替代旧工作计划、检查门闩与 checkpoint。`team.run_finished` 仅表示一条消息处理结束，`waiting` 可安静等待新消息；历史等待或失败不会锁定当前状态。`team.objective_completed` 表示店长确认可交付，验证范围按交付原文保留，更新目标后继续跟进。

原生对话输入框上方的“当前工作进展”按实际消息与执行回执原位更新，不随聊天滚走，区分发送、接收、答复和任务交付，最多显示两项优先进展。工具动作只有相应记录时才出现；超过一分钟没有新执行反馈、缺少有效时间或同步失败时不维持忙碌动画。已交付后的追问仍可显示处理中，任务结束且没有待答或在途工作后收起。查看过程与刷新只读，暂停沿用已有控制接口；后台执行不锁聊天输入框。详细行为见[对话式协作](../docs/team-chat.zh-CN.md)。

团队聊天保留用户原话、伙伴 `kind: 'message'` 的沟通与 `msg.said` 的公开角色发言。同一轮中工具回执明确关联且全文完全相同的消息只显示一次；assignment 显示轻量交接通知，可展开正文，report 不重复显示。团队追问和讲解仍从普通聊天框发送，旧任务保留独立提问入口。工具调用与模型用量在“成果与过程”的团队进度中按实际回执展示，工具发起但未返回时保留等待状态。回归测试全部模拟 API，不需要真实模型或数据库；现有分块性能测试使用 `write: false`，不会生成或同步内置 assets。

- 工作台只是事件流的对话投影，不是第二份事实来源。
- 人类方向、任务指派、Agent 产出、决策与失败都会进入可检查的事件链。
- 界面默认先分发任务并启动一轮协作；是否进入治理仍由真实分歧和风险信号决定。
- 本机检查来自显式 `cater verify` 或可选的[自动浏览器检查器](../docs/browser-checks.zh-CN.md)，和成员自报分开显示；通过只说明那次执行的记录结果。浏览器操作、失败步骤和能力缺口可展开查看，不能代替独立验收。
- 每个任务与新对话各自保留内存草稿；普通草稿刷新后不保留。已发送但结果尚未确认的新建请求另在当前会话暂存最多24小时，刷新后可用原标识重试，不自动重发。迟到的请求不会切换用户当前对话，发送期间的新输入不会被清空。
- 对话工具栏的问号入口在原聊天框提问，讲解草稿独立保存；回答可展开查看原文引用、版本和限制，不修改任务目标或验收。配置店长模型后，普通输入也会经过当前任务内的语义分流；长期群聊多任务归属仍待接入，详见[交付追问](../docs/questions.zh-CN.md)。
- 任务本可按标题或编号查找，并筛选未完成与已完成任务。查找只改变列表，不切换当前聊天或删除草稿；手机通过放大镜按需展开。完成记录后的新一轮执行仍归未完成。
- 成果正文可从聊天和成果板打开、复制、下载。阅读器使用 Radix Dialog 与 react-markdown，演示内容明确标识为“演示样例”。正文合同见 [可读成果说明](../docs/artifacts.zh-CN.md)。
- “今天在店里”打开独立伙伴页。营业依据是本次服务生命周期中的近期调用记录；演示、待确认和休假分开，不猜供应商订阅或余额。刷新只读取本地状态，不调用模型。成功观察五分钟后过期，页面可见时每分钟刷新一次，打开伙伴页时也刷新；读取失败会撤回营业声明。
- 对话上方的“本次伙伴”按需展开该任务的负责人与复核人；全店目录只保留右上角入口。点名填入当前草稿，不自动发送或伪造参与记录。
- “任务脉络”在原生消息协作中显示实际委托、子委托、回报与版本复核关系，支持缩放、平移、列表与原文详情；通信关系不冒充严格任务依赖。旧计划任务仍显示实际工作项依赖。两种图均只读，不通过拖线改变计划，不执行委托或重试；目前没有跨任务关系图。
- 页面可见时独立刷新轻量任务摘要，使用 ETag/304 避免稳定状态下反复读取历史；其他窗口的任务更新不会切走当前聊天或清空草稿。对话计数对应“全部”聊天气泡，不包含规划/交付的技术回执。

界面视觉与交互的设计基线见 [DESIGN.zh-CN.md](DESIGN.zh-CN.md)。每轮 UI 改动先更新设计判断，再检查手机、平板和桌面的真实画面。
